# 0003. 기술 구조 (앱·AI 코어·DB·에이전트·모델)

## 상황
2명이 2주 안에 화면, 서버, AI 코어를 동시에 만들어야 한다. AI 코어는 지휘 에이전트가 사건 진행을 정하고 기능별 서브에이전트와 코드 도구를 부르는 구조로 가기로 했다. 그래서 다음을 먼저 정해야 한다: 앱 기술, DB, 에이전트 프레임워크와 실행 기록, 모델, 개발 환경, 폴더, 그리고 에이전트에게 맡길 일과 코드로 고정할 일의 경계. 둘 다 Python·React·Java·JS·SQL을 쓸 수 있어 숙련도는 기준에서 뺐다.

## 비교한 선택지

### 1) 앱
| 안 | 좋은 점 | 나쁜 점 |
|---|---|---|
| **FastAPI + React·TypeScript(Vite), 패키지 uv** | AI 코어와 같은 Python. Pydantic 스키마에서 OpenAPI가 자동으로 나오고, 화면 TS 타입을 거기서 뽑는다. 화면 반응성 | 언어가 둘 |
| Spring + React | 익숙한 구조 | AI 코어(Python)와 언어가 갈라져 스키마를 두 번 쓴다 |
| Streamlit 등 Python 화면 | 빠르게 화면이 나옴 | 사건·결과를 다시 여는 웹 앱(PRD 3.4)과 화면 반응성에 약함 |

### 2) DB
| 안 | 좋은 점 | 나쁜 점 |
|---|---|---|
| **Postgres 하나 (표 + jsonb + pgvector)** | 사건–문서–문단, 법령–판본–조각처럼 연결이 많은 자료에 맞음. 판본·시점 거르기와 벡터 검색을 한 쿼리로(pre-filter). docker compose 서비스 하나 | 한국어 키워드 검색(BM25)은 기본 기능에 없어 따로 둔다 |
| Postgres + 별도 벡터 DB (Qdrant·Chroma) | 벡터 기능이 많음 | 저장소가 둘. 우리 문헌 양에는 이득이 작음 |
| Neo4j (그래프 DB) | 그래프 질의가 쉬움 | 저장소가 하나 더. M2에는 그래프를 만들지 않아 안 쓴다. M3에 그래프를 넣기로 하면(11/24 판단) Neo4j 방향으로 간다. 그래프는 인터페이스 뒤라 그때 붙일 수 있음 |

### 3) 에이전트 프레임워크·실행 기록
| 안 | 좋은 점 | 나쁜 점 |
|---|---|---|
| **LangGraph** | 지휘 → 서브에이전트 → 검증을 상태 흐름으로 짠다. 단계 검증, 사람 확인 전 멈춤, 발표용 흐름 그림이 쉬움 | 배울 것이 있음 |
| 모델 SDK 도구 루프를 직접 감싸기 | 가볍고 고장 찾기 쉬움 | 지휘·서브·검증·멈춤을 우리가 다 짠다 |
| Claude Agent SDK | 에이전트 기능이 많음 | 파일·터미널 도구가 기본이라 우리 일에 과함 |

| 실행 기록 | 좋은 점 | 나쁜 점 |
|---|---|---|
| **Langfuse (docker compose 안에 직접 띄움)** | 기록에 통지서 내용이 들어가도 우리 환경 밖으로 안 나감 | Postgres 말고도 ClickHouse·Redis·S3 호환 저장소를 같이 띄워야 함 (권장 4코어·16GB) |
| LangSmith | 설정이 쉬움 | 기록이 외부 클라우드로 감 |

### 4) 모델
| 안 | 좋은 점 | 나쁜 점 |
|---|---|---|
| **전부 Haiku 5.5로 시작, LLM 저지는 OpenAI** | 예산 안에서 많이 돌려 볼 수 있음. 성능은 프롬프트·에이전트 설계로 올린다. 저지가 채점 대상과 다른 회사라 자기 답을 후하게 볼 위험이 작음 | 어려운 단계(F4)에서 성능이 모자랄 수 있음 |
| Sonnet 5.5 기본 + 전처리만 Haiku | 단계마다 성능이 높음 | 비용이 커서 실험 횟수가 줄어듦 |

### 5) 구조: 사건 진행을 누가 정하나
| 안 | 좋은 점 | 나쁜 점 |
|---|---|---|
| **지휘 에이전트 + 기능별 서브에이전트 + 코드 도구** | 사건마다 다른 진행(더 찾기, 멈추기, 사람에게 묻기)을 에이전트가 정함. 기능별로 나눠 만들고 평가할 수 있음 | 흐름이 고정이 아니라 테스트·평가가 어려움 → 꼭 지킬 선은 아래 "에이전트가 정하는 것과 코드로 고정하는 것"처럼 코드로 고정 |
| 고정 파이프라인 (F1 → F3 → F2 → F4 순서 코드) | 단순하고 예측 쉬움 | 빠진 자료·보류·다시 찾기를 사건마다 다르게 못 함 |
| 에이전트 하나가 전부 | 짜기 쉬움 | 문맥이 길어지고 기능별 평가가 어려움 |

## 결정

### 기술
| 칸 | 고른 것 |
|---|---|
| 서버 | FastAPI, 패키지 uv |
| 화면 | React + TypeScript (Vite). 타입은 서버 OpenAPI에서 뽑는다 |
| DB | Postgres 하나: 표 + jsonb + pgvector. 그래프는 M2에 만들지 않는다. M3에 넣기로 하면 Neo4j 방향 (11/24 판단) |
| 에이전트 | LangGraph. 모델 호출은 어느 경우든 `core/llm/` 한 곳으로 |
| 실행 기록 | DB `runs`·`agent_steps`가 먼저(M1). Langfuse는 docker compose 안에 띄움 (LangSmith 안 씀). M2 초 |
| 모델 | 전부 Haiku 5.5로 시작. LLM 저지는 OpenAI로 시작하고, OpenAI 비용이 예산(3만 원)을 넘으면 Anthropic 모델로 바꾼다. 모델 이름·회사는 단계마다 설정 파일에 두고 코드에 쓰지 않는다 |
| 개발 환경 | docker compose (Postgres·pgvector·Langfuse). 둘이 같은 환경 |
| 실행 위치 | 로컬 docker compose로 시작. 발표용 웹 주소는 발표 형태를 정할 때 본다 |
| CI | PR마다 GitHub Actions로 테스트·린트 |

### 모델·저지와 함께 지킬 것
1. 핵심 단계(F4 방향·초안) 몇 건은 Haiku와 Sonnet을 비교해 "모델을 키우면 좋아지나"를 기록한다.
2. 저지를 바꾸면 비교할 점수는 같은 저지로 다시 매긴다 (섞지 않음). 저지는 채점 대상과 다른 모델로 하고, 사람 검수 표본으로 저지가 맞는지 확인한다.
3. 점수마다 저지 모델 이름을 남긴다.

### 폴더
```
src/patent_ai/
  api/            라우터만 (로직 없음)
  core/
    schemas/      결과 스키마, 근거·상태
    agents/       지휘 에이전트, 근거 검토 에이전트(F2 비교 실험: 역할 분리 있음/없음), 공통 루프·도구 규약
    f1_oa_reader/        F1 도구
    f2_legal_research/   F2 서브에이전트와 도구
    f3_claim_compare/    F3 서브에이전트와 도구
    f4_response_draft/   F4 서브에이전트와 초안 검사(코드)
    verify/       단계별 검증 도구 (F2·F3·F4 공통)
    llm/          모델 호출 모듈
  retrieval/      검색 (bm25, 벡터, graph/ ← 인터페이스 뒤)
  law_api/        법령·판례·KIPRIS 받아오기 (캐시·호출 상한)
  db/             DB 모델·마이그레이션
web/              화면
prompts/  config/  eval/  experiments/  scripts/
tests/            fixtures/ = 가짜 결과 파일
docs/
data/             git 밖
```
- 부르는 방향은 `api → core → retrieval·law_api·db`만이다. 화면은 `api`만 본다. AI 코어는 앱(api·web)을 모른다.
  - 부르는 방향에 `retrieval → db`를 더한다. db는 retrieval을 import하지 않는다. (11/18, 이슈 #65 검색 계약: 검색 저장소가 조각 표 DB 모델을 읽음)
- 서브에이전트는 각 기능 폴더 안에 둔다. `core/agents/`는 지휘·근거 검토·공통 루프만.
- 신규성은 F3·F4 안에서 처리한다 (폴더 따로 없음).
- 비교 실험(F2·F3)의 각자 구현은 같은 인터페이스 뒤에 두고 설정 파일의 `impl`로 고른다. 그래프 검색(M3, 조건부)도 넣게 되면 인터페이스 뒤에 둔다.

### 에이전트가 정하는 것과 코드로 고정하는 것
- **에이전트가 정한다:** 사건 진행. 무엇을 어떤 순서로 할지, 더 찾을지 멈출지, 사람에게 물을지.
- **에이전트가 골라 부르는 코드 도구** (답이 정해진 일이라 LLM에게 시키지 않음): 번호 정규화, 날짜 계산, PDF 파싱, 판단 단위 나누기, 청구항 비교.
- **에이전트와 상관없이 무조건 도는 코드 단계** (에이전트가 건너뛸 수 없음):
  - 초안 검사: 인용 번호·문단·조문 불일치, 거절이유별 대응 누락
  - 출처 확인: F2·F3가 사건에 근거를 넣을 때, 그 출처가 저장된 자료에 있고 쪽·문단·조문 위치가 맞는지 코드가 확인한다. 안 맞으면 넣지 않고 "확인되지 않음"으로 둔다. 그 근거가 주장을 뒷받침하는지는 근거 검토 에이전트가 본다
  - 사람 승인 전 멈춤: 사람이 고르기 전에는 다음 단계로 가지 않는다
  - 자동 조회 "대상 OA 시점까지만" 자르기: 이력 순서·발송번호·접수번호로 자르고, 날짜만으로 자르지 않는다
  - 상한: 재조회 횟수, 한 번 실행의 시간·비용. 도달하면 "확인되지 않음"과 찾아본 범위를 남기고 끝낸다. 숫자는 실제로 돌려 본 뒤 정하고 설정 파일에 둔다
- **판단 단위 나누기:** 기본 묶기는 코드 도구가 한다. F1 결과(거절이유마다 대상 청구항·인용문헌)와 청구항 판(독립/종속, 인용하는 앞 청구항)만 보고 규칙대로 묶는다. 진보성·신규성은 독립항 하나 + 그 종속항(신규성은 이 순서로 보되 결과는 청구항마다 남긴다, [ADR 0001](0001-ai-amended-claim-draft.md)), 명확성은 청구항 하나. 여러 항을 인용하는 종속항은 묶음마다 들어간다(가지). 입력이 같으면 결과가 같아 정답 세트와 바로 비교할 수 있다. 대응 방향 채점은 청구항마다 하고, 기본 묶기는 이 도구를 채점할 때만 쓴다 (#9, [대응 방향 정답](../evaluation/f4-direction-gold.md)). 묶음 안에서 대응이 갈려 더 나눌지는 지휘 에이전트가 정하고 부모 단위로 남긴다. LLM은 OA를 읽는 일(F1)과 더 나누는 판단에만 쓴다.
- 고정 단계는 위 목록만 둔다. 늘리면 고정 파이프라인이 되므로, 더할 때는 이 문서를 고친다. 그래프 테스트로 고정 단계가 늘 도는지 확인한다.
- 단계별 검증 지점(대비 뒤 / 법률 근거 뒤 / 초안 뒤) 중 어느 것을 무조건 도는 단계로 둘지는 기능 설계에서 정한다. 초안 검사는 위처럼 무조건 돈다.

## 결과
- 쉬워지는 것: 결과 스키마(Pydantic) 하나에서 API 응답, OpenAPI, 화면 TS 타입, 가짜 결과 파일이 같이 나온다. 화면·서버·AI 코어를 동시에 만든다. DB가 하나라 개발 환경을 맞추기 쉽다. 모델은 설정만 바꿔 비교한다.
- 어려워지는 것: LangGraph를 배워야 한다. 저지를 Anthropic 모델로 바꾸면 채점 대상과 같은 회사가 되므로, 다른 모델을 쓰고 사람 검수 표본으로 다시 확인한다. 에이전트 흐름이 사건마다 달라 평가가 어렵다 → 단계별 평가와 무조건 도는 코드 단계로 막는다. 한국어 BM25는 Postgres 밖(Python)에 둔다.
- 다시 볼 조건:
  - LangGraph로 뼈대를 반나절 시험해 막히면 SDK 도구 루프 직접 감싸기로 바꾼다.
  - Haiku로 F4 비교에서 차이가 크면 그 단계만 모델을 올린다 (설정 파일).
  - M2 끝(11/24)에 CQ를 보고 M3에 그래프를 넣기로 하면 Neo4j 방향으로 간다 (인터페이스 뒤라 저장소만 붙임). 안 넣으면 바꿀 것 없음.
- 이 결정으로 CLAUDE.md "특허 도메인 규칙"의 사건 진행·코드 도구 줄은 이 문서로 옮겼다 (규칙 문장 하나가 설계 판단을 과하게 묶어서).
