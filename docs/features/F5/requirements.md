## 무엇
변리사가 사건 화면에서 보는 모든 AI 결과에, 그 값을 원문에서 확인했는지(확인됨 / 확인되지 않음 / 조회 범위 내 없음 / 충돌)와 근거 위치가 붙어 있고, 사람이 판단할 것은 AI 결과와 다르게 보인다.
자료가 빠져도 할 수 있는 작업은 끝까지 하고, 멈춘 작업과 그 작업이 기다리는 자료를 "검토할 사항" 한곳에서 본다.

F5는 혼자 도는 단계가 아니라 **F1~F4 모든 결과에 걸리는 규칙과 그 표시**다. 규칙은 F1~F4 전부에 쓰고, M1 합격 확인은 F1 결과(①`OAResult`, ⑥`CaseMaterials`)로 한다. F2~F4 문서는 이 문서를 가리키고 그 기능에만 다른 것만 쓴다.

## 사용 장면 (1~3개)
1. 변리사가 거절이유별 정리를 훑다가 값 하나 옆의 상태 표시를 보고, "확인됨"이면 무엇을 확인했는지·원문 몇 쪽인지 보고 넘어가고, "확인되지 않음"·"충돌"이면 그 값만 원문과 대조하려 한다.
2. 변리사가 인용문헌 하나를 시스템이 못 가져온 사건을 열고, 나머지 결과는 그대로 쓰면서 무엇이 멈췄고 무엇을 올리면 이어지는지 한곳에서 보려 한다.
3. 변리사가 결과를 보면서 "AI가 낸 것"과 "내가 직접 판단해야 하는 것"(날짜·기한, 지원 안 하는 거절이유, 대응 방향 선택)을 섞지 않고 가르려 한다.

## 입력과 출력
- **입력 자료:** 새 자료 없음. F1~F4가 낸 결과 스키마(①~⑤)와 사건 자료(`documents`, 조회 결과).
- **필요한 판:** 해당 없음 (판을 고르지 않는다. 각 기능이 고른 판을 `evidence.edition`으로 받아 보여 주기만 한다).
- **출력:**
  - 모든 결과의 공통 칸 `status`·`evidence`·`origin`·`needs_recheck`·`flags` ([data-model.md](../../data-model.md) 3절, 코드 `core/schemas/common.py`, #14에서 들어감).
  - ⑥ `CaseMaterials`: 빠진 자료 `missing`, 보류한 작업 `held_tasks`, 검토할 사항 수 `review_items_count`.
  - 검토할 사항 목록 `ReviewItem[]` (코드 `core/schemas/propagation.py`의 `collect_review_items`). 지금은 개수만 ⑥에 있고 목록을 화면에 주는 칸이 없다 → F5 design.md 3-2절에서 ⑥에 더한다.
- **예시:** `tests/fixtures/case_missing_citation/` (인용문헌 1건 본문 없음, 있음). 더할 것은 design.md 9절.

## 합격 기준 (테스트로 바꿀 수 있게)
1~3은 [product.md](../../product.md) 5절 F5와 같다. 아래 줄은 그 기준을 테스트로 바꾼 것이다.

1. 모든 결과에 확인됨 / 확인되지 않음 / 조회 범위 내 없음 / 충돌 중 하나를 붙이고, "확인됨"에는 무엇을 확인했는지 적는다. (필수)
   - 데이터: 네 값 밖의 status, 이유 없는 "확인되지 않음", `checked` 없는 "확인됨", 찾아본 범위 없는 "조회 범위 내 없음"은 저장 전에 거부된다. ← `tests/core/schemas/test_common.py` (#14, 있음)
   - 데이터: 쪽이 있는 값은 그 쪽 글자에 원문이 있어야 한다 (확인하지 않은 원문 위치 0건, product.md 6절). ← F1 `llm/hallucinated.json` (#18, 있음)
   - 화면: 네 값이 다 든 사건을 열면, 상태 네 값이 글자와 모양(색만이 아님)으로 구분되고, 근거 위치(`evidence`·쪽)가 있고 원문에서 확인된 값에만 "원문" 위치 링크가 있고(확인되지 않음·충돌 값의 쪽은 누르면 그 쪽이 열리는 "후보 위치 N쪽" 링크, 조회 범위 내 없음·쪽 없는 값에는 링크 없음), "확인됨"이면 `checked` 글을, "확인되지 않음"이면 이유를, "조회 범위 내 없음"이면 찾아본 범위를 같이 보인다. ← `case_missing_citation` + 네 값이 다 든 화면 fixture로 브라우저 스크린샷 (#19)
2. 사람이 판단할 것(방향 선택, 법적 적용)과 AI 결과를 구분해 보인다. (필수)
   - 데이터: AI가 만든 결과는 `origin = ai_generated` 또는 `ai_default`, 사람이 고르거나 고친 것은 `human_selected`·`human_edited`이고, 고치면 AI 원본을 같이 남긴다 (data-model 3절).
   - M1에서 "사람이 판단할 것"으로 따로 보이는 것:
     - 날짜·제출기일: 원문 글자만 보이고 "직접 확인"을 붙인다 (F1 합격 기준 2, AI가 날짜를 확정하지 않음).
     - 직접 검토 필요 `needs_human_review`: 지원 안 하는 거절이유·지원 안 하는 나라 인용문헌.
     - 출원번호 입력 기다림 (실행 `waiting_for_human`, F1 실패할 때).
   - M3 (F4) 규칙만 지금 정함: 대응 방향은 "AI 기본값"(1등 후보 미리 선택)과 "사람이 고름"을 다르게 보이고, 직접 판단 필요 `needs_human_judgment` 묶음은 미리 고르지 않는다 (product.md 5절 F4 2). 구현은 #43.
   - 화면 어디에도 "적용된다"·"등록 가능"·"적법" 같은 법적 결론 글자를 AI 결과로 보이지 않는다 (CLAUDE.md 특허 도메인 규칙).
   - ← 화면 fixture에 `needs_human_review` 1건 + 날짜 칸을 넣고 열면, 스크린샷에서 날짜 칸에 "직접 확인", 그 거절이유에 "직접 검토 필요" 띠가 보이고, AI 결과의 "AI" 표시와 다른 모양이다 (#19)
   - ← 금지 낱말 검사: `grep -rnE "적용된다|등록 가능|적법|거절 해소" web/src` → 0줄 (#19)
3. 빠진 자료가 있어도 할 수 있는 작업은 끝까지 하고, 보류한 작업과 필요한 자료를 한곳에 모아 보인다. (필수)
   - 데이터: 빠진 자료마다 `missing` 한 줄, 그 자료에 **실제로 기대는** 작업만 `held_tasks`에 들어가고(data-model 3절 규칙 1), 기대지 않는 작업은 결과가 나온다. ← `case_missing_citation`: 인용문헌 2건 중 1건 없음 → 그 문헌 F3 대비만 보류 (#14·#16, 있음)
   - 데이터: 지원 안 하는 나라 인용문헌은 "올려 주세요"를 띄우지 않는다 (`ask_upload=false`, 있음).
   - 데이터: 결과 0개여도 빠진 자료 줄은 검토할 사항에 나온다 (있음).
   - 화면: "검토할 사항 N건" 한 곳에 확인되지 않음·충돌·다시 확인 필요·직접 검토/판단 필요·빠진 자료가 모이고, 줄마다 결과 안의 그 값으로 가는 링크, 빠진 자료 줄은 "올려 주세요"가 있다. ← 스크린샷 (#19)
   - 데이터: N = 검토할 사항 목록 줄 수 = ⑥ `review_items_count`. 목록은 ⑥ 안에 저장한다 (F5 design.md 3-2절). ← 개수와 줄 수가 다르면 저장 전에 거부
   - 데이터: 확인되지 않은 앞 입력에 기대 `input_unverified`가 된 칸은 결과마다 한 줄로 묶고, 원인 줄(처음 확인되지 않은 값)은 따로 낸다. ← 글자 없는 OA: 원인 줄 1 + 묶은 줄 1 (칸마다 줄 아님)
   - 데이터: 출원번호 입력 기다림은 검토할 사항 줄이 아니라 실행 상태(`waiting_for_human`)로 사건 머리에 보인다. (M3) 확신 낮은 F4 묶음은 `held_tasks`가 아니라 `needs_human_judgment` 줄로 검토할 사항에 나온다.
   - 데이터: 빠진 자료를 올리면 ⑥을 다시 써서 그 빠진 자료 줄과 그 보류가 사라진다. ← `case_missing_citation`에 그 문헌을 올린 뒤 ⑥ (다시 쓰는 함수 #140, 올리기 API 연결 #16)

- AI 지표 칸: 해당 없음 (F5는 모델을 부르지 않는다. "없는 출처 0건·확인하지 않은 위치 0건"은 각 기능 평가에서 잰다).
- 낱말 뜻: **검토할 사항** = 사람이 봐야 할 줄 하나(`ReviewItem`). "조회 범위 내 없음"은 정상 답이라 넣지 않는다. **보류한 작업** = 빠진 자료 때문에 시작하지 않은 작업 하나(`HeldTask`). 사람 선택을 기다리는 F4 묶음도 보류지만 `held_tasks`가 아니라 `needs_human_judgment` 줄로 같은 검토할 사항에 보인다.

## 근거
- 이 기능 결과의 근거: F5가 근거를 새로 찾지 않는다. 각 기능 결과의 `evidence{document_id, page·문단·조문, raw_text, edition, checked_on}`를 그대로 보인다.
- 앞 기능 결과가 "확인되지 않음"이면: 규칙 1대로 그 결과에 실제로 기대는 뒤 결과는 "확인되지 않음(`input_unverified`)"이 되고, 검토할 사항에는 **원인 줄**(처음 확인되지 않은 값)과 결과마다 묶은 한 줄이 나온다 (합격 기준 3).

## 사람이 고르거나 고치는 곳
- F5 화면에서 사람이 고치는 값은 없다 (중간 결과는 사람이 고치지 않음, product.md 3.3절).
- 사람이 하는 것: 빠진 자료 올리기, 출원번호 넣기, (M3) 대응 방향 고르기. 이 셋이 F5 보류를 푸는 길이다.
- "다시 확인 필요"가 붙은 결과를 다시 돌릴지는 사람이 정한다 (자동으로 다시 돌지 않음).

## 실패할 때
- **결과에 상태가 없거나 네 값 밖일 때:** 저장 전에 거부한다. 화면은 상태 없는 값을 "확인됨"으로 그리지 않는다 (모르면 "확인되지 않음"으로 그린다).
- **근거 위치가 원문에 없을 때:** 링크를 보이지 않고 "확인되지 않음"으로 둔다 (위치를 지어내지 않음).
- **빠진 자료의 기대는 작업을 모를 때:** 작업을 보류하지 않고 결과를 "확인되지 않음"(이유 `input_unverified`)으로 둔다. [가정] M1에서 기대는 작업은 F1 requirements 합격 기준 4의 네 갈래뿐이다 → F2~F4 설계 때 늘린다.
- **검토할 사항을 모으다 실패할 때:** 개수 0으로 보이지 않는다. 사건 화면에 오류(실패 이유)를 띄운다 (화면 `RouteError`).
- **실행이 `failed`일 때:** [가정] 이전 결과를 지우지 않고, 실패 이유와 함께 이전 결과가 "이전 실행 결과"임을 보인다 (API가 가장 최근 성공 실행 결과를 줌, data-model 5절) → #57에서 다시 봄.

## 비교 실험
아니오 (product.md 3.1절). 모델을 부르지 않는 규칙·표시 기능이다.

## 화면 흐름과 API
- 화면: 사건 열기 → 결과마다 상태 표시·근거 링크 → "검토할 사항 N건" 펼치기 → 줄을 눌러 그 값으로 이동 / 빠진 자료 줄에서 "올려 주세요" → 올리면 그 줄과 보류가 사라짐.
- API (명세 [api/README.md](../../api/README.md)):
  - 있음: `GET /cases/{id}/materials` (⑥), 각 결과 엔드포인트의 공통 칸.
  - 더할 것: ⑥에 검토할 사항 목록 칸 (엔드포인트는 그대로) → F5 design.md 3-2절. 서버 담당 리뷰로 확정.

## 안 할 것
- 상태·근거를 새로 판단하기: F5는 각 기능이 정한 상태를 모으고 보여 줄 뿐, 원문 대조는 각 기능이 한다.
- 사람이 중간 결과의 상태를 바꾸기 (예: "확인되지 않음"을 사람이 "확인됨"으로) (product.md 3.3절).
- 실행·수정 이력(C4), 수정 뒤 다시 확인(C2) (product.md 3.3절).
- 보류한 작업을 자동으로 다시 돌리기 (사람이 정함, 규칙 2).
- M1에서 "다시 확인 필요" 달기: 빠진 자료에 기대는 결과(F3 대비)가 M1에는 없다 (보류돼 결과가 없음). F3 설계(M2)에서 구현한다.
- 법적 적용·등록 가능성 표시.
