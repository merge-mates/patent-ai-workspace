# F1 OA 읽기·거절이유별 정리 requirements (기능 명세)

## 무엇
변리사가 받은 국내 OA(의견제출통지서) PDF 하나를 올리면, 시스템이 출원번호로 나머지 사건 자료를 대상 OA 시점까지만 모으고, 거절이유마다 조항·대상 청구항·인용문헌·인용 식별번호를 OA 원문 위치(쪽)와 함께 정리해 보여 준다.
못 읽은 값은 지어내지 않고 "확인되지 않음"으로, 지원하지 않는 거절이유는 "직접 검토 필요"로 보인다.

## 사용 장면 (1~3개)
1. 변리사가 OA를 막 받고, 대응 계획을 세우려고 거절이유가 몇 개이고 어느 청구항·인용문헌에 걸렸는지 한눈에 보려 한다.
2. 변리사가 정리 결과의 값 하나(예: 대상 청구항)가 맞는지 의심될 때, 그 값의 OA 원문 쪽을 눌러 원문과 대조하려 한다.
3. 변리사가 같은 사건의 두 번째 OA를 받아, 앞 OA 대응(보정서) 뒤의 청구항 판을 기준으로 새 OA를 정리하려 한다.

## 입력과 출력
- **입력 자료:** 의견제출통지서 PDF 하나 (사용자가 올림). 나머지(행정 이력, OA 당시 청구항, 최초 명세서, 인용문헌)는 출원번호로 자동 조회(#54)하고, 못 가져온 것만 사용자가 올린다. 데이터 카드: 의견제출통지서 카드는 #21에서 쓴다 (#18 구현 전에 필요. 테스트는 지어낸 글자라 카드 없이 시작)
- **필요한 판:** 대상 OA의 심사 대상 청구항 판(OA 당시 청구항). 대상 OA 뒤의 보정서·청구항 판·등록공보 청구항은 쓰지 않는다. 법령·심사기준 판은 F1에서 쓰지 않는다 (조문 번호만 읽음).
- **출력:** [`docs/data-model.md`](../../data-model.md) 4절 ① `OAResult`, ⑥ `CaseMaterials`의 F1 부분(자료들·빠진 자료). 칸 모양은 [design.md](design.md) 3-2절.
- **결과 스키마 공통 칸 (이슈 #14 제안, 11/18 인터뷰. 확정은 #14 PR에서 상대 리뷰):**
  - `status`는 객체 `{value, reason, checked, searched_scope}`. `value`는 네 값(`confirmed` / `unverified` / `not_found_in_scope` / `conflict`)만. `unverified`면 `reason` 필수, `confirmed`면 `checked`(무엇을 확인했나) 필수, `not_found_in_scope`면 `searched_scope` 필수.
  - `unverified` 이유: `lookup_failed`(조회 실패) / `body_missing`(본문 미확보) / `edition_unknown`(판본·적용 시점 모름)에 `not_extracted`(못 뽑음) / `ambiguous`(애매함) / `input_unverified`(기대는 앞 입력이 확인되지 않음, data-model 3절 규칙 1)를 더한다.
  - "다시 확인 필요"는 status 값이 아니라 결과의 별도 칸 `needs_recheck: bool` + 이유. "직접 판단 필요"·"직접 검토 필요"는 `flags` 목록.
  - 결과 전체 status는 칸들의 status를 모아 정하고, API 응답 바깥 `status`는 그 값을 복사한다. 모으는 순서는 design.md 3-2절.
- **예시:** 지어낸 통지서 텍스트 `tests/fixtures/f1/` (공개 통지서 모양을 흉내 낸 가짜 글자만, 실제 OA 원문은 넣지 않음). 목록은 design.md 9절.

## 합격 기준 (테스트로 바꿀 수 있게)
1. 표본 OA에서 출원번호·발송번호·통지일·제출기일·거절이유 조항·대상 청구항·인용문헌 번호·인용 식별번호, (있으면) 「특허 가능한 청구항」 목록과 【보정에 관한 참고사항】을 뽑고, 필드마다 OA 원문 위치(쪽)를 붙인다. (필수) ← `tests/fixtures/f1/` 기본 통지서, tune 세트 필드별 정확도
2. 뽑지 못했거나 애매한 필드는 "확인되지 않음"(이유 `not_extracted` / `ambiguous`)으로 남기고 지어내지 않는다. 날짜·법적 기한은 자동으로 확정하지 않고 원문 글자와 위치를 남긴다. (필수) ← 필드가 빠진 가짜 통지서에서 지어낸 값 0건, 확인하지 않은 원문 위치 0건
3. 청구항 하나에 거절이유가 여럿이면 모두 연결한다. (필수) ← 청구항 1이 29조 2항과 42조 4항 2호에 같이 걸린 가짜 통지서
4. 조회하지 못했거나 올리지 않은 자료(예: 인용문헌 1건 없음)를 표시하고, 그 자료에 기대는 작업만 보류한다. (필수) ← 인용문헌 2건 중 1건이 없는 fixture: 없는 인용문헌의 F3 대비만 보류, 나머지 인용문헌·거절이유는 진행
   - 기대는 작업 (F1에서 생기는 것): 인용문헌 X 없음 → X를 쓰는 F3 대비만 보류 / OA 당시 청구항(심사 대상 판) 없음 → 그 OA의 F3·F4 전체 보류 / 최초 명세서 없음 → F4 보정 근거 위치만 보류 (product.md 8절) / OA 글자 없음(스캔본) → 그 OA의 F3·F4 전체 보류.
5. 지원 유형이 아닌 거절이유는 "직접 검토 필요"로 보인다. (필수) ← 42조 3항이 섞인 가짜 통지서
6. 통지 종류(최초거절이유통지 / 최후거절이유통지)를 OA 원문에서 읽어 표시하고, 모르면 "확인되지 않음"으로 둔다. (필수) ← 최후 표시가 있는 가짜 통지서 → `final`, 최후 표시가 없는 가짜 통지서 → `initial`, 머리말이 잘린 가짜 통지서 → `unknown`
   - 정답 형식([docs/evaluation/f1-oa-gold.md](../../evaluation/f1-oa-gold.md) 2.1, PR #91)과 같게: 코드 값은 `initial` / `final` / `unknown`. KIPO는 최후 통지에만 "최후거절이유통지" 표시를 붙이므로, 머리말을 읽었는데 표시가 없으면 `initial`(최초, 원문 글자 없음 → 쪽 없음, 이유를 남김). 머리말을 못 읽었을 때만 `unknown` + "확인되지 않음".
   - 이력(앞 보정서 유무)과 맞춰 보는 것은 F1 읽기가 아니라 사건 자료 묶기(#16)가 하고, 안 맞으면 거기서 "충돌"로 둔다.
7. 올린 사건 자료와 정리 결과를 저장하고, 사건을 다시 열면 이어서 볼 수 있다. 뒤 기능(F2~F4)의 결과도 같은 사건에 저장한다. (필수) ← 서버 API 테스트 (#55·#56)
8. 사건 자료는 출원번호 + 발송번호(OA) / 접수번호(보정서)로 묶고 날짜만으로 합치지 않는다. 자동 조회와 올린 자료는 대상 OA 시점까지만 사건에 넣는다(이력 순서·발송번호·접수번호로 자름). 대상 OA 뒤의 보정서·청구항 판·등록공보 청구항은 사건 자료에 0건이고, 시점을 정할 수 없는 자료는 "확인되지 않음"으로 둔다. (필수) ← OA 둘인 사건 fixture: OA ① 실행 입력(코어에 넣는 사건 자료)에는 그 뒤 보정서·청구항 판이 없고, OA ② 실행 입력에는 있다
9. (AI) tune 세트에서 필드별 추출 정확도 ≥ [확인 필요: M1 기준선 측정 뒤] (필수). 지어낸 값·확인하지 않은 원문 위치는 문턱과 상관없이 0건.

- 낱말 뜻 (2·9번): **지어낸 값** = 정답이 "없음"인데 값을 냈거나, 원문에 없는 값을 낸 것. **확인하지 않은 원문 위치** = 값의 원문 글자가 붙은 쪽의 추출 글자에 그대로(공백·줄바꿈만 무시) 없는 것.
- 8번의 "사건 자료"는 OA마다 코어에 넣는 **실행 입력**이다. 사건 화면(`GET /cases/{id}`, ⑥)은 올라온 OA 중 가장 늦은 OA 시점까지 보인다. 테스트 fixture 둘: OA 둘인 사건 (OA ① 입력에 그 뒤 보정서·판 없음, OA ② 입력에 있음), 이력에 순서·번호가 없는 자료가 섞인 사건 (그 자료 `unverified`).
- 1~8은 product.md 5절 F1과 같다 (8번은 이 PR에서 product.md에도 더함, 11/18). 9번은 틀의 AI 기준 칸이고 product.md 6절 F1 평가에서 왔다.
- 1번 심사관 힌트: 정답 형식(PR #91)에 칸이 있고 "없으면 없음, 지어내면 틀림"으로 채점한다.

## 근거
- 이 기능 결과의 근거: 대상 OA PDF의 쪽(필드마다 원문 글자 + 쪽). 사건 자료의 판은 행정 이력의 순서·발송번호·접수번호.
- 앞 기능 결과가 "확인되지 않음"이면: F1이 맨 앞이라 앞 기능이 없다. OA 글자 추출이 "확인되지 않음"(스캔본 등)이면 필드는 모두 `unverified`(이유 `input_unverified`)이고 뒤 작업(F3·F4)은 보류된다.

## 사람이 고르거나 고치는 곳
- 출원번호를 OA에서 못 읽으면 사람이 출원번호를 넣는다 (`PATCH /cases/{id}`). 그 밖의 F1 결과(중간 결과)는 사람이 고치지 않는다 (product.md 3.3절).
- 조회하지 못한 자료는 사람이 올린다 ("올려 주세요").
- 날짜·제출기일은 사람이 원문을 보고 판단한다 (AI는 원문 글자와 위치만).

## 실패할 때
- **출원번호를 아직 모를 때 (올린 직후):** 출원번호를 읽기 전에도 올린 파일을 잃지 않는다. 사건은 "출원번호 확인되지 않음"으로 만든다 (파일 자리는 design.md 5절).
- **출원번호를 끝내 못 읽을 때:** 실행은 `waiting_for_human`(기다리는 것: 출원번호)으로 멈춘다 (방향 고르기는 실행을 멈추지 않는다, #70). 기다리는 동안 OA 필드 추출은 끝까지 하고 자동 조회만 보류한다. 사람이 출원번호를 넣으면 저장한 OA 정리로 같은 실행이 이어 돈다. 기다리는 항목은 출원번호·발송번호 둘이다 (#70).
- **읽은 출원번호의 사건이 이미 있을 때:** 새 사건을 만들지 않고 그 사건의 다음 OA로 붙인다 (발송번호가 다를 때). 올릴 때 받은 임시 `case_id`의 사건은 지우지 않고 "합침(기존 사건 ID)" 표시를 달아 사건 목록에서 숨기고, 실행(`GET /runs/{id}`)에 최종 `case_id`를 남긴다. 화면은 그 `case_id`를 연다 (아래 중복과 같은 방식, 11/18 확인). 올린 OA가 이미 있는 OA보다 앞선 OA면 이력 순서대로 끼워 넣는다 (8번: 날짜가 아니라 이력 순서·발송번호, 11/18 확인).
- **같은 OA를 다시 올렸을 때:** 같은 파일(해시)이면 올리는 요청(`POST /cases`, `POST /cases/{id}/oas` 둘 다)에서 바로 409 `{code: "oa_already_exists", case_id, oa_id}`. 다른 파일인데 읽어 보니 출원번호 + 발송번호가 같으면, 실행은 `failed`(code `oa_already_exists`, 기존 `case_id`·`oa_id` 포함)로 끝내고, 먼저 만든 임시 사건은 지우지 않고 "중복(기존 사건 ID)" 표시를 달아 사건 목록에서 숨긴다. 화면은 오류의 기존 ID로 기존 사건을 연다.
- **자료가 빠졌을 때:** 그 자료를 "빠진 자료"(⑥)에 올리고 그 자료에 기대는 작업만 보류한다 (합격 기준 4).
- **자동 조회가 실패할 때 (오류·호출 상한):** 그 자료 `unverified(lookup_failed)`, 다시 조회하거나 올리게 한다. 조회는 됐는데 출원이 나오지 않으면 `not_found_in_scope`(찾아본 범위)로 두고, 출원번호를 확인하라는 안내와 미공개 출원은 지원하지 않는다는 안내를 보인다 (product.md 3.4절).
- **한국·미국 밖 인용문헌:** 조회하지 않고 "지원 안 함, 직접 확인"(⑥ 조회 결과 "지원 안 하는 나라")으로 둔다. "올려 주세요"를 띄우지 않는다 (product.md 3.2절).
- **원문을 못 읽을 때 (스캔본, 글자 층 없음):** 실패로 끝내지 않고 글자 추출을 "확인되지 않음"(이유 `body_missing`)으로 두고, 필드는 `input_unverified`.
- **모델 호출이 실패할 때:** 상한·재시도는 모델 호출 모듈(#13). 끝내 실패하면 실행은 `failed`와 이유. 조용히 빈 결과로 성공하지 않는다.
- **거절이유가 0개로 나올 때:** 빈 목록을 이유 없이 돌려주지 않는다. 경고를 남기고 결과 status를 `unverified`(이유 `not_extracted`)로 둔다.

## 비교 실험
아니오 (product.md 3.1절). 한 사람 배정. 필드 추출 방식은 tune 세트 점수로만 본다.

## 화면 흐름과 API
- 화면: OA PDF 올리기 → 실행 상태 보기("통지서 읽는 중", "인용문헌 2건 조회 중") → 거절이유별 정리 보기(값마다 원문 쪽 링크, 상태 표시) → 빠진 자료 "올려 주세요"에 파일 올리기.
- API (명세 [api/README.md](../../api/README.md), 바뀌는 곳은 design.md 3-2절 표. 서버 담당 리뷰로 확정):
  - `POST /cases` (같은 파일이면 409 `oa_already_exists`), `POST /cases/{id}/oas`, `PATCH /cases/{id}` (출원번호 넣기, 새로 더함)
  - `GET /cases/{id}`: 사건 + OA 목록 + 사건 이력·청구항 판 요약 (칸은 design.md 3-2절)
  - `GET /oas/{oa_id}/oa-result` (① `OAResult`), `GET /cases/{id}/materials` (⑥)
  - `GET /documents/{id}` (쪽 텍스트), `GET /documents/{id}/file` (원본 PDF, 새로 더함)

## 안 할 것
- F1 결과를 사람이 고치기 (product.md 3.3절).
