## 무엇
OA 흐름(F1 → 단위 나누기 → F2·F3 → F4)은 코드가 정한 순서로 돈다. 그 안에서 **근거를 못 찾은 곳**이 생기면 결과를 보며 질의·검색 방법을 바꿔 다시 찾는다. 두 곳이다.
- (가) 인용문헌 다시 찾기: F3 대비 1차에서 근거 문단을 하나도 못 고른 구성요소.
- (나) 최초 명세서 보정 근거 찾기: F4가 대응 방향을 고르기 전, 보정에 쓸 수 있는 특징과 그 명세서 위치.

찾은 문단 ID를 내거나, 다 찾고도 없으면 지금처럼 "조회 범위 내 없음"과 찾아본 범위(질의·검색 종류·k)를 남긴다. 상한·실패로 끝까지 못 찾았을 때만 "확인되지 않음"으로 보류한다. 변리사는 구성요소마다 어떤 질의로 몇 번 찾았고 무엇을 열어 봤는지를 단계 기록으로 본다.
다시 찾는 방법은 세 가지를 같은 인터페이스 뒤에 두고 설정으로 고른다: 지금 방식(같은 질의로 한 번 더 깊이) / 고정 루프(코드가 판정 → 질의 다시 쓰기 → 다시 검색) / 에이전트 루프(모델이 결과를 보고 다음 검색을 고름). 어느 것을 기본으로 쓸지는 비교 숫자로 정한다.

## 왜 여기만 에이전트 후보인가
- 진행 순서(어느 기능을 부를지)는 거절이유 종류와 자료 유무로 정해진다 → 코드. 11/23 tune 10통 fixed_order 실행에서 끝까지 돈 9통이 모두 같은 순서(F1 → F3 → F2 → F4)였다 (git 밖 일회용 실행, 저장소 실험 카드 없음. ADR 0004 상황).
- 다시 찾기는 앞 검색 결과를 봐야 다음 질의를 정할 수 있다 → 미리 규칙으로 다 못 정한다 → 에이전트(tool use 루프)를 둘 만한 자리.
- 그래도 고정 루프가 이미 많이 올릴 수 있다 (LLM 질의 다시 쓰기만으로 인용문헌 Hit@10 0.706 → 0.79 수준. 출처: 이슈 #225 안건 9 본문, 저장소 실험 카드 없음. 0.706은 [m2-i2 hybrid 카드](../../../experiments/m2-i2-cite-search-hybrid-rrf/card.md)). 그래서 에이전트는 고정 루프보다 나을 때만 쓴다 (합격 기준 7).

## 사용 장면
1. 변리사가 진보성 OA를 올렸는데 1차 검색에서 근거를 못 고른 구성요소가 있을 때, 다른 말(상위 개념·동의어·기능 표현·도면 설명)로 다시 찾은 문단을 받으려고. (지금 `second_search`는 같은 질의로 상위 20까지와 도면 설명 조각을 한 번 더 볼 뿐 질의를 바꾸지 않는다)
2. 변리사가 "보정 + 반박" 방향을 볼 때, 보정에 넣을 특징이 최초 명세서 어디에 있는지 위치와 함께 받으려고. (지금 F4 방향 프롬프트는 명세서를 보지 않고, 보정 초안 단계만 명세서를 본다)
3. 팀이 "지금 방식 / 고정 다시 찾기 루프 / 에이전트 루프"를 같은 세트로 잰 표를 보이려고 (포트폴리오, 에이전트가 필요한 곳인지의 근거).

## 입력과 출력
- **입력:** 판단 단위(묶음) 하나(`JudgmentUnit`) + (가) 1차에서 근거를 못 고른 구성요소 글자와 대상 청구항 글자 / (나) 차이점 구성요소·대상 청구항 글자·심사관 요지. 찾는 곳은 (가) 그 OA 인용문헌의 조각(색인 `cite_chunks`, 그 문헌만) / (나) 그 사건 최초 명세서 문단.
- **필요한 판:** OA 당시 청구항, 최초 명세서(출원서). 등록공보·다른 사건 의견서는 넣지 않는다.
- **출력:** 결과 키는 지금 그대로(`run_f3`·`run_f4`).
  - (가) F3 대비 줄의 근거 문단을 채운다. 변리사는 그 근거가 다시 찾기에서 나왔고 어떤 방식·질의로 찾았는지 줄에서 알아본다. 다시 찾기가 본 결과도 검색 기록에 남아 채점기가 센다 (모양은 design.md 5절).
  - (나) F4 입력에 `amendment_basis`(특징 글·명세서 문단 ID·이유) 칸을 더하고, 방향·보정 프롬프트 변수로 넘긴다.
  - 단계 기록에 도구 이름·인자(질의 글, k, 문단 ID)·결과 ID, 묶음 ID·구성요소 ID.
- **예시:** `tests/fixtures/e2e/` 사건 + 가짜 응답(FakeTransport) 테스트, E2E는 기록된 모델 응답.

## 합격 기준
1. (가) `recheck`가 `none`이 아닌 실행에서 1차에 근거를 못 고른 구성요소만 다시 찾기가 맡는다. 방식(B·C)과 상관없이 각 구성요소는 셋 중 하나로 끝난다: 근거 문단 ID / "조회 범위 내 없음" + 찾아본 범위 / 보류(이유 코드). 다른 구성요소의 결과는 바뀌지 않는다 (필수, 가짜 응답 테스트).
2. (나) `spec_basis`가 `none`이 아닌 실행에서 진보성·신규성 묶음에 F3 차이점 후보(진보성 표의 `differences`, 신규성은 "차이 있음" 구성요소)가 있으면, 방향을 고르기 전에 명세서 근거 찾기가 돌고 결과가 F4 방향·보정 프롬프트 변수 `amendment_basis`에 들어간다 (필수).
3. 에이전트가 낸 문단 ID는 그 문헌(또는 명세서)에 실제 있고 그 대화에서 연 것만 받는다. 없는 ID·다른 문헌 ID·안 연 문단·목록 밖 도구·스키마 밖 인자는 도구 결과로 오류와 고칠 방법(교정 지시)을 돌려주고, 상한 안에서 다시 고르게 한다 (필수).
4. 다시 찾기 중에 구성요소(또는 묶음) 하나가 도구 호출 상한이나 모델 차례 상한에 닿으면 그 구성요소만 `limit_reached`로 보류하고 실행은 이어 간다. 찾아본 질의 목록을 남긴다 (필수).
5. 다시 찾기가 도구를 부르면 호출마다 도구 이름·인자(질의 글, k, 문단 ID)·결과 ID가 묶음 ID·구성요소 ID와 함께 단계 기록에 남는다. 원문 문단 글은 기록에 넣지 않는다 (필수).
6. `recheck`·`spec_basis`를 켠 실행에서도 새 멈춤은 없다. 사람을 기다리는 것은 지금처럼 `check_oa` 번호 확인뿐이다 (필수).
7. (AI) 같은 세트·같은 커밋에서 A(지금 방식) / B(고정 루프) / C(에이전트 루프)를 돌려 `search_recall`·`selected_recall`(1차에서 못 찾은 구성요소만 따로 한 줄)·F4 `direction_top1`·호출 수·토큰·비용·시간·구성요소당 도구 호출 수·`give_up`·`limit_reached`를 한 표로 낸다. 판정 규칙(design.md 7-3, 분모 = 1차에 못 찾은 구성요소가 있는 정답 줄 수 n을 카드에 같이 적는다. n이 작아 0.05가 한두 줄 차이면 노이즈 범위 점수를 같이 본다): C가 B보다 높고 그 차이가 같은 판 2회 흔들림보다 크면(최소 0.05 [가정]) C, 비슷하면 싼 쪽, 지면 C를 쓰지 않고 이유를 실험 카드와 design.md 8절에 남긴다 (필수. 판정용 2회는 두 사람 환경을 맞춘 뒤, 이번 이터레이션은 smoke 1회).
8. (AI) (나)가 찾은 명세서 위치가 F4 정답의 "명세서에서 가져온 보정" 줄(`added_from`의 `spec:[식별번호]`, tune F4 정답 파일에 있는 꼴. 정답 문서 [f4-direction-gold](../../evaluation/f4-direction-gold.md) 예시에는 `claim:N`만 있어 spec 꼴은 [가정])과 맞는 비율 (있으면 좋음).

## 근거
- 다시 찾기는 새 법률 판단을 하지 않는다. 기본(`recheck_judge: compare`)은 문단을 "찾아 내는" 데까지이고, 대비 판정(같다/다르다)은 지금 F3 대비 단계(compare)가 그 문단으로 다시 한다. 에이전트가 판정까지 내는 판(`recheck_judge: agent`)은 비교용 스위치로만 둔다 (design.md 8절 D4).
- 못 찾음 ≠ 없음: 다 찾고도 없을 때는 지금 F3와 같이 "조회 범위 내 없음" + 찾아본 범위(PRD F3 3번)다. 다시 찾기는 그 범위를 넓힐 뿐 상태 규칙을 바꾸지 않는다. 상한·호출 실패·검색 실패로 끝까지 못 본 것만 "확인되지 않음" 보류다 (이유 코드는 design.md 5절).

## 먼저 끝나야 하는 것 (다른 기능·사람에 기대는 것)
- ADR 0004(제안)에 대한 은진 님 동의 (확정 전에는 스위치 기본값을 `none`으로 둔다).
- `agent_steps` 두 칸 마이그레이션 리뷰 (합격 기준 5).
- F4 입력 `amendment_basis` 결과 스키마 칸 리뷰 (합격 기준 2, `core/schemas/` 공유 자원).

## 사람이 고르거나 고치는 곳
- 다시 찾고도 없는 구성요소: 지금처럼 "조회 범위 내 없음" + 찾아본 범위로 보인다. 보류된 구성요소(상한·실패)는 지금 F3 보류 표시 그대로 보인다.
- 보정 근거: 변리사가 고르는 대응 방향 화면에 위치와 함께 후보로만 보인다. AI가 보정 적법성을 판정하지 않는다.

## 실패할 때
- 검색 색인이 비었거나 검색이 실패할 때: 경고 + 그 구성요소 보류(`tool_failed`), 조용히 성공하지 않는다.
- 모델 호출이 재시도 뒤에도 실패할 때: 그 구성요소 보류(`model_call_failed`), 1차 결과는 그대로 둔다.
- 최초 명세서가 없을 때: (나)를 건너뛰고 F4는 지금처럼 돈다 (`amendment_basis`는 "확인되지 않음: 명세서 없음").

## 비교 실험
예. 한 사람(재아)이 구현하고 같은 인터페이스 뒤에서 설정으로 바꿔 같은 세트로 비교한다: (가) `recheck: none | fixed_loop | agent`, (나) `spec_basis: none | fixed_loop | agent` (기본 둘 다 `none` = 지금과 같음. 판 B·C는 둘을 같은 값으로 돌린다).
- 다른 축 (스위치): `recheck_judge: compare | agent`(다시 판정을 F3 대비 단계가 하나 에이전트가 하나), `reflect: 0 | 1`(Reflexion 한 번 더, 판 C+R), `supervisor: code | llm`(위에 LLM supervisor를 두는 판 D), 검색 범위(그 OA 인용문헌 / 노이즈 범위).
- 정해진 값: 에이전트 모델은 지금 F3와 같은 모델·effort, 더 큰 모델은 선택 축. 상한 숫자는 [가정]으로 시작하고 smoke 뒤 잰 숫자로 고친다 (design.md 4-4).

## 화면 흐름과 API
- 화면: 안 바뀜. (나) 보정 근거 위치는 F4 방향 후보의 근거 칸에 붙일 수 있다 (있으면 좋음).
- API: 안 바뀜. 단계 기록(DB `agent_steps`)에 `unit_id`·`tool_input` 칸이 붙는다 (마이그레이션, design.md 6절. 지금 `GET /runs/{id}` 응답에는 단계 줄이 없어 API 모양은 그대로).

## 안 할 것
- 사건 전체 진행을 LLM이 정하기 (ADR 0004에서 버린 대안).
- 다른 사건 의견서 검색(정답 누출), 그 OA 인용문헌 밖 새 선행문헌 검색 (PRD 3.3 범위 밖).
- 고객 보고·대응 여부 결정, 실행 중 사람에게 묻기.
- 모델 학습 (반성 토큰 학습, 궤적 SFT).
- F2 안의 법률 근거 찾기 방법 바꾸기: F2 주인이 정한다 (design.md 3-1).
