## 무엇
변리사가 OA 하나를 올려 F1(거절이유별 정리)·F3(대비)·F2(법률 근거)까지 돌면, AI가 판단 단위(묶음)마다 대응 방향 후보를 순위·이유·확신도와 함께 보여 주고 1등을 미리 골라 둔다.
변리사가 묶음마다 방향을 확인하거나 바꾸면, 고른 방향으로만 의견서 초안과 (보정이 있으면) 검토용 보정 청구항 초안 + 최초 명세서 근거 위치를 받는다. 확신이 낮은 묶음은 순위 없이 "직접 판단 필요"로 두고 그 묶음 초안만 보류한다.

- **판단 단위(묶음):** 거절이유 × 단위. 진보성·신규성은 독립항 묶음, 명확성은 청구항 하나 ([ADR 0001](../../decisions/0001-ai-amended-claim-draft.md) 11/17 보완, [product.md](../../product.md) 3.2절). 묶음은 F3 단계가 만든 `JudgmentUnit`(②)을 그대로 쓴다.
- **의견서:** 출원인이 거절이유통지에 대해 내는 의견 서면. **보정서:** 명세서·청구범위를 고치는 서면. F4는 둘 다 "검토용 초안"까지만 만든다.

## 사용 장면 (1~3개)
1. 변리사가 진보성 지적 두 묶음(청구항 1~5, 청구항 6~8)을 받고, 묶음마다 "종속항 3 특징을 독립항에 합치기 / 보정 없이 차이점 반박" 같은 후보를 순위·이유·확신도로 보고 고객 보고 전에 검토 순서를 잡으려 한다.
2. 변리사가 1등 후보를 그대로 두거나 다른 후보로 바꾼 뒤, 의견서 초안과 보정 청구항 초안(바뀐 부분 + 최초 명세서 근거 위치)을 받아 직접 고쳐 쓰려 한다.
3. 변리사가 최후거절이유통지 사건에서 보정이 범위 줄이기·오기 정정·명확화·이전 보정 되돌리기 안에서만 제안되는지, 확신이 낮아 "직접 판단 필요"로 남은 묶음이 어디인지 한눈에 보려 한다.

## 입력과 출력
- **입력 자료 (OA 하나):** 사용자가 직접 올리는 자료는 없다. 앞 단계 결과와 사건 자료를 받는다.
  - F1 ① `OAResult`: 거절이유·대상 청구항·통지 종류·심사관 힌트(「특허 가능한 청구항」 목록, 【보정에 관한 참고사항】).
  - F3: 판단 단위 ② `JudgmentUnit`, 진보성·신규성 대비표 ③ `ComparisonTable`, 명확성 검토 `ClarityReview`.
  - F2 ④ `LegalEvidenceBundle` (묶음마다). **OA 흐름에서 F2는 지휘 에이전트가 부르고, F3는 대비만 한다 (11/21 재아 결정).** 지휘 설정 기본은 `plan: agent`(모델이 다음 도구를 고름)이고, `plan: fixed_order`일 때만 F1 → F3 → F2 → F4 순서로 돈다 (`config/orchestrator.yaml:2-4`, 커밋 059429c). F2가 아직 없으면 묶음마다 빈 법률 근거 묶음("확인되지 않음")을 쓴다.
    - ④를 묶음에 잇는 키: 지금 F4는 `unit_id`가 같은 ④만 찾고, 없으면 경고 없이 빈 묶음을 쓴다 (`src/patent_ai/core/f4_response_draft/inputs.py:73-78`). F2는 ④를 거절이유마다 만들어 `oa_id`·거절이유 순번으로 저장하므로(F2 design 2절, [data-model.md](../../data-model.md) 4절 ④), 그대로 붙이면 F2 근거가 모든 후보에서 조용히 빠진다. 규칙은 [design.md](design.md) 3-1절. F2 연결(이슈 #29) 전에 코드를 고친다.
    - 질문: `plan: agent`일 때 지휘가 F4를 언제 부르나 (F3·F2 결과가 다 있을 때만인지 등). 지금은 모델이 고르고 규칙이 없다 (`src/patent_ai/core/agents/orchestrator.py:5`, 커밋 059429c).
  - 사건 자료: OA 당시 청구항 글자, 최초 명세서 쪽 글자, 확인 기준일. 데이터 카드는 F1·F3와 같다 ([product.md](../../product.md) 8절 F1·F3·F4 줄).
- **필요한 판:** 대상 OA의 심사 대상 청구항 판(OA 당시 청구항). 보정 근거 위치는 최초 명세서(출원서, 없으면 공개공보). 등록공보는 AI 입력에 넣지 않는다 ([product.md](../../product.md) 8절). 보정 제한은 F1이 읽은 통지 종류(최초/최후)를 따른다.
- **출력:** [`docs/data-model.md`](../../data-model.md) 4절 ⑤ `DirectionCandidates`(묶음마다 하나)와 `Drafts`(의견서·보정 청구항 초안, OA 하나에 하나. data-model.md 4절에는 이름만 있고, 칸은 코드 `src/patent_ai/core/schemas/drafts.py`와 [design.md](design.md) 3-2절). 한 번 실행의 결과는 도구 출력 `F4Output`에 한데 담긴다 (저장 스키마 아님). 칸은 [design.md](design.md) 3-2절.
- **예시:** 지어낸 사건 `tests/fixtures/f4/case_basic.json`, 가짜 응답 `tests/fixtures/f4/llm/*.json`, 지어낸 명세서 `tests/fixtures/f4/spec_basic.pages.json`. 실제 OA·청구항 글자는 넣지 않는다 (CLAUDE.md).

## 합격 기준 (테스트로 바꿀 수 있게)
1~7은 [product.md](../../product.md) 5절 F4 1~7과 같다 (번호도 같음). 아래 "점수 기준"은 5절 밖, 6절 F4 평가에서 왔다.

1. 판단 단위마다 대응 방향 후보(최대 개수는 설정)를 만들고 순위·이유·확신도(높음/중간/낮음)를 붙인다. 각 후보에 거절이유별 대응·보정 핵심·근거·확인 사항을 붙이고, 확인 사항에는 "보정하면 권리범위가 얼마나 줄어드나"를 넣는다. 후보는 고객 보고 요약으로도 읽히게 쓴다. 순위는 검토 순서 제안이고 등록 가능성을 보증하지 않는다고 표시한다. 확신이 낮으면 순위 없이 "직접 판단 필요". 심사관 힌트를 읽고 후보에 쓴다. (필수)
   ← `tests/core/f4/test_f4_directions.py` (단위마다 결과 하나, 확신 낮음 = 순위 없음, 상한 넘음 = 출력 검사 실패, 보증 아님 문구). tune 실행에서 37단위 모두 후보나 "직접 판단 필요"가 있음 (실험 카드 [`experiments/m3-f4-skeleton/card.md`](../../../experiments/m3-f4-skeleton/card.md)).
   - "권리범위가 얼마나 줄어드나" 확인 사항, 고객 보고 요약 문체, 심사관 힌트 쓰기는 프롬프트 문구(`prompts/f4/direction.md:17-18, 26`)라 테스트하지 않고 tune 결과로 본다.
   - 질문: 확신도 높음·중간·낮음을 무엇으로 가르나, 기준값은 설정 파일의 어느 키인가. 지금은 모델이 매기고 코드는 "낮음이면 순위 없음"만 지킨다.
   - 질문: 후보 최대 개수 3(`config/f4.yaml` `max_candidates`)을 그대로 둘지. ADR 0001은 "돌려 본 뒤 정한다".
2. 묶음마다 1등 후보가 AI 기본값으로 미리 선택된다. 사람은 다른 후보로 바꿀 수 있고, 고르지 않으면 1등 후보로 초안을 만든다. 초안은 사람이 고칠 수 있다. 화면과 데이터에서 AI 기본값과 사람이 고른 것을 구분한다. 확신 "낮음" 묶음은 미리 고르지 않고 사람이 고를 때까지 그 묶음 초안만 보류한다. (필수)
   ← `test_f4_directions.py::test_1등_후보가_AI_기본값으로_미리_선택된다`, `::test_확신이_낮으면_순위_없이_직접_판단_필요이고_미리_고르지_않는다`, `test_f4_run.py::test_한_묶음만_확신_낮음이면_나머지는_진행한다`
   - 사람이 고른 후보(`human_selected`)로 초안을 만드는 테스트는 아직 없다. 사람 선택 뒤 초안을 다시 만드는 길은 이슈 #70 ([design.md](design.md) 3-2절 질문).
3. 고른 방향으로만 의견서 초안을 만든다. 구성: 사건 정보 → 지적 요지 → 대응과 근거 → (보정이 있으면) 보정 설명 → 마무리. (필수)
   ← `test_f4_opinion.py::test_고르지_않은_후보는_프롬프트에_들어가지_않는다`, `::test_의견서_칸은_정해진_순서이고_AI_원문이_비지_않는다`
4. 보정이 있으면 검토용 보정 청구항 초안과 바뀐 부분, 최초 명세서 근거 위치를 보인다. 적법성은 판단하지 않는다고 표시한다. (필수)
   ← `test_f4_amendment.py::test_바뀐_청구항마다_보정_초안과_명세서_근거_위치가_있다`, `::test_명세서에_없는_근거는_버리고_확인되지_않음으로_둔다`, `::test_바뀐_부분은_앞뒤_글자를_비교해_낸다`, `::test_적법성을_판단하지_않았다는_문구가_상수로_있다`
5. 초안의 인용 번호·문단·조문이 F1~F3 결과와 맞는지 검사하고 안 맞는 곳을 표시한다. 대응 누락은 "모든 거절이유 × 모든 대상 청구항"으로 검사한다. (필수)
   ← 누락 검사: `test_f4_run.py::test_판단_단위가_덮지_않은_청구항은_거절이유와_함께_나온다`, `::test_대상_청구항을_못_읽은_거절이유는_누락_검사를_못_했다고_남긴다`. 번호·문단·조문 불일치 검사는 아직 없음 (이슈 #40).
   - 질문: 초안 검사 문제 목록의 칸(문제 종류·위치·기대값·실제값·심각도 등)과 저장 자리 (이슈 #40).
6. 최후거절이유통지이면 보정 초안을 범위 줄이기·오기 정정·불명확한 기재 명확화·이전 보정 되돌리기 안에서만 만들고 그 제한을 표시한다. 통지 종류를 모르면 확인을 요청한다. (필수)
   ← `tests/core/f4/test_f4_final_limit.py` (스위치 켬 + 최후 → 보정 프롬프트에 제한 + 결과 표시, 켬 + 모름 → 확인 필요, 끔 + 최후 → 후보마다 "보정 제한을 적용하지 않은 초안 (최후거절이유통지, 직접 검토 필요)" + `needs_human_review`). 제한을 지켰는지는 코드가 판정하지 않는다.
   - 스위치 `final_rejection_limit`은 기본 켬이다 (11/21 재아 결정, 커밋 14d26fb, `config/f4.yaml`). 끄는 것은 비교 실험 설정으로만 쓴다.
7. 묶음별 선택이 서로 부딪히지 않는지 사건 전체를 검사한다 (독립항 보정이 종속항에 번짐, 삭제 뒤 인용 번호, 여러 독립항을 "또는"으로 인용하는 종속항의 가지). 지원하지 않는 거절이유가 섞여 있으면 "AI가 다루지 않은 거절이유가 남아 있음, 직접 대응 필요"를 띄운다. (필수)
   ← 지원 안 하는 거절이유: `test_f4_run.py::test_지원_안_하는_거절이유는_번호를_남기고_status는_나빠지지_않는다`. 한 청구항이 두 묶음에 걸칠 때 뒤 묶음이 덮어쓰지 않음: `test_f4_amendment.py::test_앞선_묶음이_가진_청구항을_뒤_묶음이_덮어쓰지_않는다`. 번짐·삭제 뒤 인용 번호·가지 엇갈림 검사는 아직 없음 (이슈 #39).
   - 같은 청구항을 두 묶음이 고쳐 뒤 묶음 초안을 싣지 않으면 `F4Output.amendment_overlaps`에 남기고 확인 글에도 적는다 (커밋 a9421df). 지원 안 하는 거절이유도 확인 글에 "AI가 다루지 않은 거절이유 N개(직접 대응 필요)"로 드러낸다 (커밋 f9ea396).
   - 질문: 사건 전체 검사의 규칙 범위(M3에 넷 다 / 일부 먼저)와 결과 칸.
### 점수 기준 ([product.md](../../product.md) 6절 F4 줄)
점수 1. (AI) tune 세트에서 대응 방향 ①②층 점수를 한 줄로 낸다 ([대응 방향 정답](../../evaluation/f4-direction-gold.md)). 주 지표는 `direction_top1` = AI 기본 선택(순위 1 후보, 순위 후보가 없는 보류 묶음은 후보 목록 첫째)의 거친 방향이 정답과 맞는 비율이다. 옛 값(목록 첫째 후보)은 `direction_top1_list_first`로 같이 낸다 (11/22 재아 결정 2, 이슈 #39). 보류(확신 낮음) 묶음도 빼지 않고 센다. 같이 내는 것: 기본 선택 후보 확신도 높음·중간·낮음별 일치율(`direction_top1_conf_*`, 목록 첫째 기준은 `direction_top1_list_first_conf_*`), 보류 비율 `needs_human_judgment_rate`, 누락 쌍. ① 다뤘나 지표(`handled_accuracy`)는 뺐다. 정답 문서에서 정의를 정한 뒤 다시 넣는다 (커밋 73fb60d, [eval/GUIDE.md](../../../eval/GUIDE.md)). 화면에서 보류 묶음의 순위를 숨기는 것은 그대로다 (11/21 재아 결정, 커밋 04cb253·999759a·e07543d). `direction_top1` ≥ 질문 (필수)
   - 질문: `direction_top1` 문턱. 기준선(정답이 생긴 뒤 첫 점수)을 잰 뒤 정하고, "특허 가능한 종속항을 독립항에 합친다" 단순 규칙 점수보다 높아야 하는지 ([product.md](../../product.md) 6.1절).
   - ③층(보정 종류·더한 구성의 출처)과 ④층(반박 논리, LLM 저지)은 아직 점수를 내지 않는다. ④는 아래 점수 2의 질문.

점수 2. (평가) 초안 주입 오류(번호·문단·조문 불일치) 20개 이상에서 초안 검사가 잡는 비율을 한 줄 낸다 ([product.md](../../product.md) 6절 F4 줄, 이슈 #40). 문턱 질문 (필수)
   - 질문: 의견서·보정서 초안 품질 기준표 (이슈 #46). 저지 기준표에서 정할 것: 글 품질도 재나 / 점수 눈금 / "논리가 같다"의 기준 / 감점 폭 / 저지에 줄 자료 / 정답 ④의 모양 / 저지 검증 기준 / 저지 모델·반복 수. PRD는 저지를 ④ 반박 논리 채점에만 쓰고 ①~③은 정답셋 점수와 맞는지로 저지를 검증한다 ([product.md](../../product.md) 6.1절). "의견서·보정서 초안 품질" 전체를 재는 줄은 PRD에 없어, 기준표를 ④만으로 둘지 초안 품질까지 넓힐지 먼저 정한다. 기준표·검수 방법은 `docs/evaluation/`에 둔다 (이번 문서에서는 쓰지 않음).

## 근거
- **후보의 근거:** 그 묶음 F3 결과(대비표·명확성 검토)에 붙은 근거만 쓴다. 모델이 낸 근거는 받지 않는다 (`src/patent_ai/core/f4_response_draft/directions.py:141-151, 213`).
  - 명확성 묶음 후보의 근거: F3 명확성 검토는 근거를 `spec_definition` 한 곳에만 넣는다(`src/patent_ai/core/f3_claim_compare/clarity.py:325-334`, 커밋 c093221). F4가 `spec_definition`도 같이 모은다 (커밋 7262264).
- **보정 청구항의 근거:** 최초 명세서의 쪽 + 원문 글자. 모델이 준 글자를 그 쪽 원문과 대조해 통과한 것만 남긴다 (`amendment.py:121-154`).
- **앞 기능 결과가 "확인되지 않음"이면:** F4는 멈추지 않고 후보·초안을 만들되, 그 결과 status를 "확인되지 않음(`input_unverified`)"으로 전파한다 (data-model.md 3절 규칙 1, `directions.py:132-138`). F2 결과가 없으면 빈 법률 근거 묶음(`unverified`, 이유 `not_extracted`)을 써서 초안이 "확인됨"이 될 수 없다. "조회 범위 내 없음"으로 쓰지 않는다 (찾아보지 않았으므로, `inputs.py:49-70`).
  - 질문: F2 근거가 "확인되지 않음"일 때 후보 확신도에 상한(예: 중간)을 둘지.
  - F3가 대비하지 못한 인용문헌(`compared = false`: 본문 미확보, 미국 문헌 등)의 상태는 지금 F4로 넘어오지 않는다. F3 대비표 status는 대비한 줄(rows)만 모으고(`src/patent_ai/core/schemas/comparison.py:103-104, 141-143`, 커밋 c093221), F4는 대비표·법률 근거 status만 전파하며 후보 flags도 확신 낮음 여부로만 정해 대비표의 `needs_human_review`를 옮기지 않는다 (`directions.py:214, 228`). 미국 문헌은 늘 본문 미확보라, F2가 붙으면 한국+미국 결합 진보성 후보가 "확인됨" + 검토 표시 없음이 된다.
  - 고치는 쪽은 F4로 정했다 (11/21 재아 결정, 공유 스키마를 건드리지 않음): `compared = false` 문헌의 `skipped_status`를 후보 status 전파에 넣고, 대비표의 `needs_human_review`를 후보 flags로 옮긴다. F2 연결(이슈 #29) 전에 고친다 ("먼저 끝나야 할 것").
  - F3 보류도 일부는 F4에서 안 보인다. 단위를 못 만든 보류(`f3_split`·`f3_units`)는 그 청구항이 어느 단위에도 없어 누락 쌍(`uncovered`)으로 보이지만, 단위 안 청구항 보류(`f3_compare:<unit_id>:claim<N>`)는 청구항 N이 단위 `claims`에 남아 누락으로 세지 않고(`coverage.py:27`), 본문 미확보 보류도 F4에서 안 보인다. 그래서 대비 안 한 청구항이 확인됨 후보에 표시 없이 묶일 수 있다. 위 `compared = false`와 같이 고친다.
  - `F3Result.held_tasks` 자체는 F4 입력에 없다. 지휘가 ⑥ `CaseMaterials.held_tasks`로 옮길 예정이고 지금 코드는 없다 (이슈 #166).
- **기대는 입력이 없을 때 보류하는 것** (F1 requirements 합격 기준 4와 같음):
  - F4 전체를 부르지 않음: OA 정리·F3 결과·OA 당시 청구항과 명세서 글자(실행 입력)·확인 기준일 중 하나라도 없으면 지휘가 F4를 "확인되지 않음(`input_unverified`)"으로 넘긴다 (`src/patent_ai/core/agents/step_inputs.py:48-57`, 커밋 059429c). OA 당시 청구항(심사 대상 판) 없음도 여기 든다.
  - 최초 명세서 없음 → 보정 근거 위치만 보류(초안 글은 남김) / 청구항 글자 일부 없음 → 그 묶음 보정 초안만 보류.

## 사람이 고르거나 고치는 곳
- **방향 고르기:** 묶음마다 후보 하나. 데이터에서 AI 기본값은 `selection.origin = ai_default`(1등만 가리킬 수 있음), 사람이 고른 것은 `human_selected`(1등과 같아도). 확신 낮은 묶음은 `selection = null`(미선택) + `needs_human_judgment` (`src/patent_ai/core/schemas/direction.py:195-207, 246-258`). 후보 자체는 늘 `ai_generated`이고 사람 선택은 `selection` 한 곳에만 둔다 (`direction.py:159-164`).
- **초안 고치기:** 의견서 칸·보정 청구항마다 AI 원문(`ai_text`)은 남기고 사람이 고친 글은 `human_text`에 따로 둔다 (`origin = human_edited`). 보류된 청구항(AI 원문 없음)은 고칠 수 없다 (`src/patent_ai/core/schemas/drafts.py:27-80`).
- **최종 채택·제출:** 사람. F4는 제출하지 않는다.
- **화면에서 사람이 판단할 것 표시:** "직접 판단 필요"(확신 낮음, 미선택 묶음), "직접 검토 필요"(근거 위치 못 찾음, 통지 종류 확인 필요, 지원 안 하는 거절이유, 누락), "순위는 검토 순서 제안이고 등록 가능성을 보증하지 않음", "검토용 초안이며 적법성은 판단하지 않음".
- 중간 결과(F1·F2·F3)는 사람이 고치지 않는다 ([product.md](../../product.md) 3.3절).

## 실패할 때
- **확신이 낮을 때:** 그 묶음만 보류(초안 없음, `held_units`에 남음). 나머지 묶음은 진행한다. 모든 묶음이 보류면 초안(`Drafts`)은 없다 (`src/patent_ai/core/f4_response_draft/run.py:70-77`, `opinion.py:246-248`).
- **모델이 후보를 0개 낼 때:** 그 묶음 결과는 "확인되지 않음" + "직접 판단 필요". 빈 목록을 성공으로 숨기지 않고 경고한다 (`directions.py:369-373`).
- **자료가 빠졌을 때:** 위 "근거" 칸의 보류 규칙. 청구항 글자가 없는 묶음은 "직접 검토 필요"를 붙인다 (`directions.py:355-359`, `amendment.py:263-278`).
- **근거 위치를 못 찾을 때:** 보정 초안 글은 남기고 근거 위치만 비운다. 그 청구항 상태는 "확인되지 않음"(명세서 없음 `body_missing` / 대조 탈락 `evidence_rejected`) + "직접 검토 필요" (`amendment.py:157-164`). 못 찾음을 "없음"으로 쓰지 않는다.
- **통지 종류를 모를 때:** 보정 제한을 짐작하지 않는다. 스위치가 켜져 있으면 후보마다 "통지 종류 확인 필요"를 붙인다 (`directions.py:344-349`).
- **묶음이 상한보다 많을 때:** 앞 `max_units`개 묶음(order 순)만 다루고, 넘는 묶음은 모델을 부르지 않고 `unverified(limit_reached)` + "직접 판단 필요"로 보류한다. 실행은 `failed`가 아니다 (정함 #211, ADR 0003 "상한에 닿으면 확인되지 않음과 찾아본 범위를 남기고 끝낸다").
- **모델 호출이 실패할 때:** 출력 검사에 떨어지면 한 번 다시 부른다. 그래도 실패하면 그 묶음만 "확인되지 않음"(`not_extracted`) + 이유로 보류하고 나머지는 끝까지 한다. 호출 상한에 닿은 묶음은 `limit_reached`로 보류한다. 시도한 모든 묶음이 실패하면 방향 후보 단계가 못 돈 것이라 예외로 올려 실행 `failed` (정함 #211). 묶음 밖 상한(F1 읽기·지휘 모델)은 이슈 #241. F3 청구항 나누기 상한은 그 청구항부터 `limit_reached` 보류 (#317).

## 비교 실험
아니오 ([product.md](../../product.md) 3.1절). 한 사람(재아) 배정. 방향 후보·초안은 tune 점수로만 본다. ADR 0003 "모델·저지와 함께 지킬 것" 1번(F4 몇 건은 Haiku와 Sonnet을 비교해 기록)은 비교 실험이 아니라 기록이다.
- 질문: 설정만 바꿔 비교할 축을 둘지 (심사관 힌트 넣음/뺌, 모델 크기 등). 힌트 있음/없음은 PRD가 따로 보이라는 점수 줄이다 (6.1절).

## 화면 흐름과 API
- 화면: 묶음별 대응 방향 후보 보기(순위·이유·확신도, 1등 미리 선택, 확신 낮음은 "직접 판단 필요") → 묶음마다 방향 바꾸기 → 의견서 초안·보정 청구항 초안 보기(바뀐 부분, 근거 위치 쪽 링크) → 초안 고치기 → 사건 전체 검사·초안 검사 결과 보기.
- API (명세 [api/README.md](../../api/README.md)):
  - `GET /oas/{oa_id}/directions` (⑤), `PUT /directions/{unit_id}/selection` (사람 선택, origin = 사람이 고름)
  - `GET /oas/{oa_id}/drafts` (초안 + 초안 검사 결과), `PATCH /drafts/{draft_id}` (사람이 고침, AI 원문 남김)
  - `GET /oas/{oa_id}/case-check` (사건 전체 검사)
  - 질문: 초안 검사 결과·사건 전체 검사 결과 응답 스키마. 명세에 "F4 설계 때"로 남아 있다.

## 안 할 것
- 방향을 고르기 전에 후보마다 초안을 미리 쓰기 (ADR 0001 확장 후보).
- 고객 보고서 생성 ([product.md](../../product.md) 5절 F4 1번: 후보를 보고 요약으로 읽히게 쓰는 데까지).
- 보정 전후 상세 비교(O9): "바뀐 부분 + 최초 명세서 근거 위치"까지만 ([product.md](../../product.md) 3.3절).
- 보정이 최후거절이유통지 제한을 지켰는지, 신규사항인지 코드나 모델이 판정하기.
- 지원하지 않는 거절이유의 대응 후보·초안 (번호와 "직접 대응 필요"만).
- 수정 뒤 다시 확인(C2): 시간이 남으면 의견서 문장 단위로만 (M3 끝에 선택).
