# 챗봇 화면(웹)과 서버 설계 — 첫 버전

작성: 2026-11-13. 상태: 사용자가 방향(단일 턴, 원문 보기, 상태 표시)을 승인함. 규모: 작은 프로젝트(서버 1개, 화면 1개, 테스트).

## 1. 의도
법령 근거로 답하는 챗봇(`src/rag`)을 브라우저에서 쓰게 한다. 사용자가 답변의 근거 조문을 눌러 **원문을 바로 확인**하고, 답이 "일부만 근거 있음"이거나 "근거 없음"일 때 그것을 화면에서 분명히 알 수 있어야 한다(변리사가 검증하고 승인하는 흐름이 핵심 가치).

## 2. 범위
- 하는 것: 질문 한 개 → 답변(`answer_display`) + 상태 표시 + 인용 조문 칩, 칩을 누르면 조문 원문과 출처(판본·시행일) 보기, 오류·대기 표시, 면책 한 줄, 라이트/다크, 휴대폰 폭.
- 안 하는 것(비목표): **대화 기억**(질문마다 독립 처리), 로그인·저장, 배포, 공보·OA·판례, 스트리밍 응답.
- 안티 목표: 모델·조문 글을 HTML로 해석해 넣는 것(XSS), 오류 응답에 키·내부 정보를 싣는 것, 근거 없음·부분 답변을 일반 답변처럼 보이게 하는 것.

## 3. 이전에 만든 간단한 챗봇 실습 코드에서 참고한 것(그대로 복사하지 않고 선별)
- 그대로: `static/md.js`(마크다운 구조 해석, 글자만 DOM으로 그림)와 그 node 테스트, 입력 처리(Enter 전송·Shift+Enter 줄바꿈·한글 입력 중 `isComposing` 검사·자동 높이), 안전한 렌더링(`textContent`만), 테마·레이아웃, 면책 한 줄.
- 같은 방식으로 새로 씀: 표준 `http.server` 서버, 주입 가능한 함수, 방어 장치(`Content-Type: application/json`만 허용, 본문 1MB·질문 1,000자 제한, 30초 소켓 타임아웃, 짧은 한국어 오류, 예외 종류만 로그, 포트 사용 중 안내).
- 안 가져옴: 실습 코드의 검색·프롬프트·정규식 인용 판별(여기서는 `src/rag`가 구조화된 `citations`를 준다), "특허법 한정" 문구.

## 4. 구조
- `src/rag/server.py`: `make_server(settings, ask, get_article_fn, static_dir)`, `handle_ask(raw, ask, settings)`, `main()`. 실행 `python -m src.rag.server` (기본 포트 3000, `CHATBOT_PORT`로 변경).
- 라우트: `GET /`·`/index.html`·`/md.js`(화면), `GET /health`, `POST /api/ask`, `GET /api/article?id=<조문 id>`.
- `POST /api/ask` 요청 `{"message": str, "history"?: list}` — **`history`는 선택 필드로 정의하고 지금은 받아서 무시**한다(나중에 대화 기억을 붙일 때 호환 유지). 응답 `{"status", "answer_display", "citations": [{"article_id","label"}], "seconds"}`(원문 응답·검색 내부·근거 본문은 보내지 않는다). 오류는 `{"error": "…"}` 400/415/502/500.
- `GET /api/article?id=` 응답 `get_article` 결과(`label`, `title`, `chapter`, `text`, `source`), 없으면 404.
- `src/rag/web/index.html`, `src/rag/web/md.js`: 화면. 인용 조문은 버튼 칩이고 누르면 원문 패널(대화상자)이 열린다(Esc·닫기 버튼, 휴대폰에서도 스크롤). 상태 표시: `partial`은 "제공된 조문으로 일부만 확인된 답변입니다" 안내, `no_basis`는 "근거를 찾지 못했습니다" 강조 표시, 오류는 오류 말풍선. 대기 문구는 "찾는 중… (보통 15~20초 걸립니다)". 첫 화면 안내에 "질문마다 독립적으로 처리됩니다. 앞 질문을 이어서 묻지 말고 전체 문장으로 입력해 주세요"를 넣는다.
- 설정: `Settings`에 `article_corpus`(`data/processed/chunks_법령3_article.jsonl`), `port`(3000), `max_message_len`(1000) 추가.
- 검색에는 항상 독립된 질문 한 문장을 넘긴다(대화 기억은 나중에 `retrieve` 앞단 전처리로 붙이는 이음새).

## 5. 확인 방법
- 서버: 가짜 `ask`로 요청 검증·오류·상태 코드·원문 조회·정적 파일·헤더 검사(실제 서버를 임시 포트에 띄워 HTTP로).
- `md.js`: 마크다운 해석기의 node 테스트(`node --test tests/rag-md.test.mjs`).
- 화면: 실제 서버를 띄워 **브라우저 스크린샷**(데스크톱·휴대폰 폭, 라이트·다크, 인용 칩 클릭 후 원문 패널, partial/no_basis 표시)으로 확인하고 파일로 남긴다(사용자 규칙).

## 6. 빌더에게 맡기는 것
CSS 세부, 패널 접근성(포커스 이동), 오류 문구, 정확한 파일 분할은 기존 실습 챗봇 구조를 참고해 정한다.

## 7. 알려진 한계
응답에 15~20초가 걸리고(검색 3회 호출 + 생성), 서버는 요청을 스레드로 처리하므로 동시 사용자가 많으면 API 비용·지연이 늘어난다. 인증·사용량 제한이 없으므로 로컬(127.0.0.1)에서만 연다. 대화 기억이 없어 후속 질문이 안 이어진다.
