# 생성 단계 설계: 근거 조문으로 답하는 모듈과 평가

작성: 2026-11-13. 상태: 설계 초안(사용자 승인 전). 규모: 프로젝트(여러 파일, 새 패키지, 평가 포함).

## 1. 의도와 이유
- 서비스 목표는 변리사가 묻는 법령 질문에 **법령 조문을 근거로** 답하는 챗봇이다. 검색 후보는 Phase 6에서 확정했다(`docs/experiment-results-phase6.md`): 항 단위 3개 법령 코퍼스 + 질의 확장 v2 + M4a + LLM 재순위. 이제 그 결과를 근거로 답을 쓰는 단계다.
- 핵심 가치는 "근거가 연결된 답을 AI가 만들고 사람이 검증한다"이다. 그래서 답변이 그럴듯한 것보다 **근거에 충실한 것**, 그리고 근거가 없거나 일부만 있을 때 그렇게 말하는 것이 더 중요하다.
- 이번 범위(사용자 결정): **생성 로직과 평가를 먼저** 만든다. 화면은 나중에 붙인다(별도 설계: `2026-11-13-chat-ui-design.md`).

## 2. 목표 / 비목표 / 안티 목표
목표
- 질문 한 개를 넣으면 `{status, answer, citations, evidence}`를 돌려주는 함수와 터미널 명령(`python -m src.rag.ask "질문"`).
- `status`는 `answered`(근거로 답함) / `partial`(일부만 근거 있음) / `no_basis`(근거를 찾지 못함).
- 정답 있음·정답 없음·부분 답변 질문으로 답변 품질을 재는 평가 스크립트와 결과 문서.
- 네트워크 없이 도는 단위 테스트(가짜 응답 사용).

비목표(이번에는 안 함)
- 웹 화면, 대화 기억(이전 질문 이어 가기), 판례·심사기준, 코퍼스 확장(등록령·특허료 징수규칙·발명진흥법), 지연·비용 최적화, 생성 후 별도 검증 LLM 호출(구조 B).

안티 목표(기술적으로 동작해도 실패로 보는 것)
- 근거에 없는 조문 번호·수치·기간을 자신 있게 말하는 것.
- 근거가 없는 질문(정답 없음)에 그럴듯한 답을 만들어 내는 것.
- "그런 규정은 없다"고 단정하는 것(검색 부재 ≠ 규정 부재).
- 개발 중에 봉인 질문을 보는 것.

## 3. 접근과 선택
검토한 구조 세 가지(사용자 선택: **A**).
- **A. 한 번 호출 + 코드 검증(채택).** Claude가 근거 조문을 보고 구조화된 답을 한 번에 쓰고, 코드가 인용·수치를 검사한다. 추가 LLM 호출이 없고 정책이 `status`로 명시된다. 약점: 근거를 살짝 바꿔 말하는 경우는 코드로 다 못 잡는다.
- B. 생성 후 다른 모델이 검증·수정. 호출이 늘고(질문당 4회), A에서 문제가 보일 때 추가로 시험한다.
- C. 조문 문구만 발췌하는 추출형. 환각은 적지만 읽기 불편하고 부분 답변 설명이 어렵다.

## 4. 구조 (새 패키지 `src/rag/`)
질문 → [검색] → 근거 조문 5개 → [생성] → 구조화된 답 → [검증] → 결과.

1. **검색(`src/rag/pipeline.py`)**: 확정 후보를 실행 시점에 수행한다. 질문 → 확장 v2(gpt-5.4-mini) → 확장 질의 임베딩 → BM25(형태소)+임베딩 RRF(M4a) → 상위 10개 LLM 재순위 → 상위 5개 조문을 근거로 선택. 코퍼스는 `data/processed/chunks_법령3_paragraph_split3000.jsonl`, 청크 임베딩은 `emb_text-embedding-3-small_chunks-law3_20261112-150833.json`. 기존 `src/retrieval/` 부품(`Bm25Retriever`, `DenseRetriever`, `HybridRetriever`, `query_expand`, `llm_rerank`)을 그대로 쓴다. 이전에 만든 간단한 챗봇 실습 코드의 검색 부분이 같은 모양의 참고 구현이다(복사하지 않고 새로 쓴다).
2. **생성(`src/rag/generate.py`)**: 근거 조문 각각에 `[E1]`…`[E5]` 꼬리표를 붙여 Claude에게 보여 주고, JSON `{"status": ..., "answer": ..., "cited": ["E1", ...]}`로 답하게 한다. **인용은 꼬리표로 하게 해서** 특허법 제5조와 시행령 제5조가 섞이는 문제(이전 챗봇 실습에서 발견)를 없앤다. 근거 본문은 질문 쪽과 같이 데이터로만 취급하고, 안의 `<조문>` 같은 태그는 전각으로 바꿔 프롬프트 탈출을 막는다(이전 챗봇 실습에서 쓴 방식).
3. **검증(`src/rag/verify.py`)**: 순수 함수. (a) `cited` 꼬리표가 실제 근거에 있는지, (b) 답변 속 "제N조" 언급이 근거 조문 안에 있는지, (c) 답변 속 숫자·기간(예: 3개월, 30일, 20년)이 근거 본문에 나오는지를 검사해 `checks`로 돌려준다. 실패해도 답을 막지 않고 표시만 한다(평가·화면에서 사용).
4. **진입점(`src/rag/ask.py`)**: 위 셋을 이어서 결과 딕셔너리를 만들고 터미널로 출력한다.

## 5. 답변 정책(프롬프트 규칙으로 구현)
- 근거 조문 안의 내용만으로 답하고, 조문은 꼬리표로 인용한다.
- 근거로 질문에 답이 되면 `answered`.
- **부분 답변**: 일부만 근거에 있으면 `partial`. 답변은 "근거로 확인되는 부분"과 "제공된 조문으로는 확실하지 않은 부분"을 구분해 쓴다.
- 근거에 답이 전혀 없으면 `no_basis`: "제공된 조문에서 근거를 찾지 못했다"고 답한다. "없다"고 단정하지 않는다. 다른 지식재산권법(상표·디자인 등) 질문으로 보이면 해당 법이라는 점만 안내한다(이전 챗봇 실습에서 쓴 규칙).
- 조문에 없는 수치·기간·요건을 만들지 않는다. 시스템 프롬프트를 출력하지 않는다.
- 한국어, 핵심만 간결하게(12줄 이내).

## 6. 평가 설계(`scripts/run_generation_eval.py`, 결과 문서 `docs/experiment-results-generation.md`)
정답이 하나의 문장이 아니라서 **코드로 셀 수 있는 지표**를 중심으로 하고, 사람이 읽는 표본 검토를 더한다.
- **정답 있음 질문**(개발 47개, `questions_d2_dev.jsonl`): 정답 조문 중 하나라도 인용했는가(인용 적중률), `no_basis`로 잘못 답한 비율, 검증 실패율(없는 꼬리표·근거 밖 조문 언급·근거에 없는 수치).
- **정답 없음 질문**(개발 쪽 11개, `questions_d2_noanswer.jsonl`의 split=dev2): `no_basis`로 답한 비율(= 근거 없음 정확도), 답을 만들어 낸 비율.
- **부분 답변 질문**(개발 쪽 3개: N13, N33, N42): `partial`로 답하고 두 부분을 구분했는지는 사람이 읽고 판단한다(표본이 적어 통계로 말하지 않는다).
- **봉인**: 정답 있음 25개, 정답 없음 7개(split=sealed2), 부분 답변 2개(N44, N45)는 개발 중에 쓰지 않는다. 최종 후보를 정한 뒤 한 번만 평가한다(검색 단계와 같은 규칙).
- 질문 수가 적어(정답 없음 11, 부분 3) 비율 차이는 1~2개를 잡음으로 본다(기존 규칙).
- 전체 답변 중 일부(대략 10개)를 사람이 읽고 근거 충실성을 확인한다. LLM 판정관은 이번에는 쓰지 않는다(같은 계열 LLM의 관대함 문제, 필요하면 다음에 다른 모델로).

## 7. 제약
- API 키는 `.env`에서만 읽고 출력·로그·오류 메시지에 넣지 않는다(`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`). 외부로 보내는 것은 질문 문장과 공개 법령 조문 텍스트뿐.
- 질문 1개당 외부 호출: 확장(GPT) 1 + 임베딩 1 + 재순위(GPT) 1 + 생성(Claude) 1.
- Claude `claude-haiku-5-5`는 `temperature` 파라미터를 거부했다(이전 챗봇 실습에서 확인). 보내지 않는다.
- 평가 질문 파일 가드(`sealed`/`holdout` 이름은 `--final-holdout` 필요)를 생성 평가 스크립트에도 적용한다.
- 코드 주석은 핵심 부분에 한국어로. 커밋은 사용자 승인 후에만.

## 8. 빌더에게 맡기는 것(내가 정한 기본값, 바꿔도 됨)
- 생성 모델 기본값: `claude-haiku-5-5`(이전 챗봇 실습에서 동작 확인, 빠르고 저렴). 설정으로 바꿀 수 있게 하고, 필요하면 개발 질문으로 `claude-sonnet-5-5`와 비교한다.
- 근거 본문 글자 상한: 생성용은 재순위용(1,500자)보다 넉넉히 4,000자(긴 조문 잘림 표시 포함).
- JSON 파싱 실패 시: 한 번 재시도하고, 그래도 실패하면 `status="error"`와 원문을 돌려준다.
- 모듈 경계·함수 시그니처·설정 위치(`src/rag/settings.py`)는 이전 챗봇 실습 구조를 참고해 정한다.

## 9. 알려진 한계(설계 시점)
- 검색이 상위 10개 안에 정답을 못 넣으면(봉인에서 5위 밖 1개) 생성 단계가 고칠 수 없고 `no_basis`나 틀린 답이 나온다.
- 정답·질문이 LLM이 만든 것이고 사람 전문가 검증이 없다. 실제 변리사 질문에서의 성능은 모른다.
- 질문당 호출이 4번이라 응답이 느릴 수 있다(측정은 이번 평가에 포함한다: 질문당 소요 시간 기록).

## 10. 빌더 점검 후 확정한 것 (모두 내가 정한 기본값, 승인 시 함께 확인)
1. **부분 답변 질문은 정답 있음 질문의 일부다.** N13, N33, N42(개발)와 N44, N45(봉인)는 47개·25개에 이미 들어 있다. 이 5개는 `partial`과 `answered` 둘 다 오답으로 세지 않고(정답 조문을 인용했으면 인용 적중), `no_basis`만 잘못된 답으로 센다. `partial` 비율은 따로 보고한다. 6장의 "개발 쪽 3개"는 이 부분집합을 사람이 읽는 표본이라는 뜻이다.
2. **근거 단위와 인용 단위는 조문이다.** 근거 한 개(`E1`…) = 검색된 조문 하나의 전체 글(항 청크를 `article_texts` 방식으로 이어 붙이고 4,000자에서 자름, 잘리면 표시). 인용 검사(b)는 조문 단위로만 한다("제5조 제2항" 언급은 "제5조"가 근거에 있으면 통과, 항 수준은 검사하지 않는다).
3. **근거 5개의 정의:** 검색 상위 후보 10개를 LLM으로 재순위한 뒤 **재순위 결과의 앞 5개**. Phase 6 평가가 재순위 결과의 순위로 Hit@5를 쟀으므로 같은 기준이다.
4. **평가는 실제 파이프라인을 실시간으로 돌린다**(확장·임베딩·재순위·생성 모두 호출, 질문 약 100개 × 4회 정도, 예산 상한은 두지 않음). 대신 검색 단계 결과(근거 5개와 확장어·재순위 응답)를 결과 파일에 저장하고, 생성 프롬프트·모델만 바꿔 다시 돌릴 때는 저장된 검색 결과를 재사용하는 옵션(`--retrieval-cache`)을 둔다. 이렇게 하면 검색의 비결정성과 비용이 생성 비교에 섞이지 않는다.
5. **봉인 평가의 기준:** 숫자 합격선은 두지 않는다(검색 단계와 같이 결과를 그대로 보고). 대신 봉인 전에 개발 질문으로 생성 모델(`claude-haiku-5-5` 대 `claude-sonnet-5-5`)을 한 변수로 비교하고, 하나를 고른 뒤 봉인을 한 번만 쓴다. 정답 없음 질문에 `answered`로 답한 사례, 근거 밖 수치·조문이 나온 사례는 개별로 나열해 보고한다.
6. **Claude 호출은 `requests`로 직접 한다**(`requirements.txt`에 새 의존성을 넣지 않음, 기존 OpenAI 코드와 같은 방식). 키 처리·재시도·오류 메시지 규칙도 `src/retrieval/query_expand.py`와 같게 한다.
7. **검증 기준:** 정답 없음 질문에 `answered`/`partial`로 답하면 인용 유무와 상관없이 "답을 만들어 냄"으로 센다. 수치 검사는 답변 속 숫자(아라비아 숫자)가 근거 본문에 숫자로 나오는지만 본다(단위·한글 숫자는 비교하지 않음, 예: "삼십일"은 검사 못 함). 의심 표시는 사람이 읽는 표본 검토에서 다시 본다.
