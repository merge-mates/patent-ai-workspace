# 3주 PRD — OA 대응 안에서 법률 근거까지 한 줄로

## 1. 한 줄
변리사가 받은 국내 OA 한 건을 올리면, 거절이유별로 정리하고, 지적마다 법령·심사기준·판례 근거를 대화로 찾아 확인하고, AI가 낸 대응 방향 2~3개 중 하나를 골라 의견서·검토용 보정 청구항 초안까지 받는다. 모든 결과에 원문 위치·판본·확인 상태가 붙는다.

비유: 집 두 채(법률 조사, OA 대응)를 따로 짓지 않고, OA 대응이라는 집 한 채를 짓고 그 안에 법률 조사 서재를 둔다. 서재는 현관(사건 없는 질문)으로도 들어갈 수 있다.

## 2. 왜 이 범위인가
- 실무 흐름(OA 받기 → 근거 확인 → 대응 방향 → 초안)이 처음부터 끝까지 보여야 시연과 평가가 설득력이 있다. (출처 없음, 판단)
- 법률 조사는 OA 화면과 단독 질문이 **같은 엔진**을 쓴다. 따로 만들지 않아 2명·3주에 맞춘다. (출처 없음, 판단)
- 표본 OA 4건에는 인용문헌과 대조해야 하는 거절이유와 청구항 문장을 봐야 하는 거절이유가 함께 있어 이 흐름을 보여 줄 수 있다. 필요한 자료는 기능에 맞춰 다시 받는다 (8절). (재아 노트 `oa_sample_citations_1113.md`)
- 결정: [ADR 0002](decisions/0002-first-build-scope.md) 확정 (2026-11-13). 의견서·보정 초안까지 넣는다 (시연 가치 우선).

### 왜 에이전트인가
- 같은 "OA 대응" 요청이라도 입력마다 다음 행동이 바뀐다: 통지 종류(최초/최후)에 따라 보정 범위가 달라지고, 거절이유 유형에 따라 문헌 대조를 할지 문장을 볼지가 갈리고, 자료가 빠지면 그 작업만 보류하고, 근거를 못 찾으면 다른 문단·도면을 다시 찾고, 판본을 모르면 다른 시점 판을 조회한다.
- 고정 파이프라인(읽기 → 요약 → 초안)으로 짜면 이 재조회·보류·확인 요청을 못 한다. 문서 하나를 넣고 묻는 RAG 챗봇은 판본 확인과 사건 자료 연결을 못 한다. (출처 없음, 판단)
- 다만 번호 정리·날짜·청구항 비교처럼 순서가 정해진 일은 코드로 한다 (저장소 CLAUDE.md).

### 3.2 지원하는 거절이유
- **미정.** 의견제출통지서 학습데이터로 거절이유별 빈도를 센 뒤 정한다. 참고로 실무 글은 진보성을 가장 흔한 유형으로 들지만 수치 근거는 없다 (재아 노트 `oa_common_rejection_web_1113.md`, 회사 블로그·개인 글).
- 정할 때 볼 것: 표본에 실제로 나오나, AI가 보여 줄 일이 있나, 변리사 없이 채점할 수 있나, 법률 근거 조사와 이어지나 (재아 노트 `oa_rejection_types_1113.md`).
- 거절이유는 AI가 하는 일에 따라 크게 둘로 나뉜다. 이 PRD는 둘 다 한 가지씩은 지원한다고 보고 쓴다: **문헌 대조형**(인용문헌과 청구항을 맞대 봐야 함, 예: 진보성·신규성) / **문장 검토형**(청구항·명세서 문장을 봐야 함, 예: 명확성). 어느 유형을 고르는지는 위 집계 뒤에.
- 지원하지 않는 거절이유도 F1 정리 화면에는 다 보이고 "직접 검토 필요"로 표시한다. AI 대조·대응 초안은 만들지 않는다.
- 인용문헌은 한국·미국 문헌만. 다른 나라 문헌은 "지원 안 함, 직접 확인"으로 표시한다.

### 3.3 3주에 안 하는 것
- 보고서 갱신·버튼 반영(L7), 보고서 내보내기(L8), 조사 기록 이어 하기(L9)
- 보정 전후 상세 비교(O9)는 F4 보정 초안 안의 "바뀐 부분 + 원명세서 근거 위치"까지만
- 최종 검토 화면의 저장·내려받기(O10), 실행·수정 이력(C4)
- 수정 뒤 다시 확인(C2): 시간이 남으면 의견서 문장 단위로만 (3주 맨 끝 선택)
- 사건 이력 자동 조회 (KIPRIS API로 당시 청구항 찾기): 사용자가 자료를 직접 올린다
- 기준 기획서 14절 확장 후보 전부 (사전 초안, AI 추가 검토 사항, 법률 조사에 OA 첨부 등)

## 4. 업무 흐름 (시연 순서)
일의 순서만 정한다. 화면 배치(무엇을 한 화면에 같이 둘지)는 이 PRD에서 정하지 않고 화면 설계에서 정한다.
1. **사건 올리기 (F1):** OA PDF, OA 당시 청구항(또는 그 판이 든 보정서), 최초 명세서, 인용문헌 PDF를 올린다. 시스템이 출원번호·발송번호로 묶고, 빠진 자료와 버전 미확인을 표시한다.
2. **거절이유별 정리 (F1):** 거절이유마다 조항, 대상 청구항, 인용문헌·지정 문단을 OA 원문 위치와 함께 보인다.
3. **대조 (F3):** 문헌 대조형 지적이면 청구항 요소별로 인용문헌 문단을 대조한다. 심사관 지적 / AI 대조 결과 / AI가 새로 찾은 문단을 나눠 보인다. 문장 검토형 지적이면 OA가 짚은 문구와 청구항·명세서 문장을 대조한다.
4. **법률 근거 (F2):** 지적에서 법률 근거 찾기를 부르면 대화가 시작된다. 질문이 미리 채워지고(예: "청구항에서 앞에 없던 '상기 ○○'를 쓰면 문제가 되나, OA 통지일 기준"), 조문·심사기준·판례를 판본과 함께 찾고, 주장별 근거와 한계를 답한다. 근거마다 원문 위치(PDF 쪽, 판결 "이유 1" 등)를 보인다. 고른 근거를 이 사건으로 가져간다.
5. **대응 방향 (F4):** AI가 사건 전체 대응 방향 2~3개를 보인다 (예: 의견만으로 반박 / 일부 거절이유는 보정, 나머지는 반박). 각 후보에 거절이유별 대응, 보정 핵심, 근거, 확인 사항.
6. **초안 (F4):** 하나를 고르면 의견서 초안과 (보정이 있으면) 검토용 보정 청구항 초안 + 원명세서 근거 위치를 만든다.
7. **상태 (F5):** 모든 결과에 확인됨 / 확인되지 않음 / 조회 범위 내 없음 / 충돌 상태와 "검토할 사항 N건"이 붙는다.
- 같은 법률 근거 엔진은 사건 없이 법률 질문만으로도 쓸 수 있다 (사건 없는 조문 질문).

## 5. 기능별 합격 기준

### F1 OA 읽기·거절이유별 정리
1. 표본 OA에서 출원번호·발송번호·통지일·제출기일·거절이유 조항·대상 청구항·인용문헌 번호·지정 문단을 뽑고, 필드마다 OA 원문 위치(쪽)를 붙인다.
2. 뽑지 못했거나 애매한 필드는 "확인되지 않음"으로 남기고 지어내지 않는다.
3. 청구항 하나에 거절이유가 여럿이면 모두 연결한다.
4. 올린 자료 중 빠진 것(예: 인용문헌 1건 없음)을 표시하고, 그 자료에 기대는 작업만 보류한다.
5. 지원 유형이 아닌 거절이유는 "직접 검토 필요"로 보인다.
6. 통지 종류(최초 / 최후)를 OA 원문에서 읽어 표시하고, 모르면 "확인되지 않음"으로 둔다. 최후 통지 뒤에는 보정할 수 있는 범위가 좁아지기 때문이다 ([보정 범위](product/domain/보정_범위.md)).

### F2 법률 근거 조사 엔진
1. 자유 질문을 받고, 시점이 없으면 현행 자료로 답하며 확인 기준일을 표시한다. 시점이 있으면 그 시점 판본 후보를 찾고, 판본을 모르면 "미확인"을 돌려준다.
2. 답변의 주장마다 출처(자료 종류·식별자·판본)와 원문 위치를 붙인다. 확인하지 않은 위치는 붙이지 않는다.
3. 판례·심결례는 전문/요지, 판단/당사자 주장을 구분해 표시한다.
4. 근거 검토: 출처가 실제로 있는지, 위치·판본이 맞는지, 원문이 주장을 뒷받침하는지를 확인하고, 안 맞으면 고치거나 "확인 필요"로 표시한다.
5. 미발견 / 조회 실패 / 본문 미확보 / 판본·적용 미확인을 구분한다.
6. OA 화면에서 부르면 지적 정보로 질문을 채우고, 사용자가 고른 근거만 사건으로 넘긴다 (출처·판본·미확인 상태 포함).

### F3 청구항–인용문헌 대조
1. 문헌 대조형 지적: OA 당시 청구항을 요소로 나누고, 요소마다 인용문헌의 관련 문단을 원문 위치와 함께 보인다. 진보성이면 그 위에 심사관·법원이 따지는 순서대로 정리한다: ① 어느 인용문헌에도 없는 요소(차이점) ② 심사관이 어떤 문헌을 주 인용·보조 인용으로 어떻게 합쳤나 ③ 명세서에 적힌 효과 중 반박에 쓸 후보 ([진보성](product/domain/진보성.md), 대법원 2007후3660 등).
2. 심사관이 지정한 문단과 AI가 찾은 문단을 구분한다.
3. 근거를 못 찾으면 다른 문단·도면을 한 번 더 찾고, 그래도 없으면 "조회 범위 내 없음"과 찾아본 범위를 표시한다 (부재로 단정하지 않음).
4. 문장 검토형 지적: OA가 짚은 문구를 청구항에서 찾아 위치를 표시하고, 명세서에 그 용어의 정의·설명이 있는지도 같이 찾아 보인다. 문제 유형을 근거와 함께 보인다 (명확성이면 예: 선행 기재 없음, 선택적 표현, 명세서와 다른 용어, [명확성](product/domain/명확성.md)).
5. 한국·미국 문헌만 대조한다. 그 밖은 "지원 안 함".

### F4 대응 방향 후보와 초안
1. 사건 전체 대응 방향 후보를 2~3개 만들고, 각 후보에 거절이유별 대응·보정 핵심·근거·확인 사항을 붙인다. 확인 사항에는 "보정하면 권리범위가 얼마나 줄어드나"를 넣는다. 후보는 변리사가 고객(출원인)에게 보고할 요약으로도 읽히게 쓴다 (고객 보고서 생성 자체는 3주 밖). 우열이나 성공 가능성은 말하지 않는다.
2. 사용자가 후보를 고르거나 고쳐 쓰거나 직접 입력할 수 있다.
3. 고른 방향으로만 의견서 초안을 만든다. 구성: 사건 정보 → 지적 요지 → 대응과 근거 → (보정이 있으면) 보정 설명 → 마무리.
4. 보정이 있으면 검토용 보정 청구항 초안과 바뀐 부분, 원명세서 근거 위치를 보인다. 적법성은 판단하지 않는다고 표시한다.
5. 초안의 인용 번호·문단·조문이 F1~F3 결과와 맞는지 검사하고 안 맞는 곳을 표시한다. 대응 누락은 "모든 거절이유 × 모든 대상 청구항"으로 검사한다 (청구항 하나라도 남으면 출원 전체가 거절되기 때문, 대법원 2022후11190).
6. 최후 통지이면 보정 초안을 범위 줄이기·오기 정정·불명확한 기재 명확화·이전 보정 되돌리기 안에서만 만들고, 그 제한을 화면에 표시한다. 통지 종류를 모르면 확인을 요청한다 ([보정 범위](product/domain/보정_범위.md)).

### F5 근거·상태 표시와 진행·보류
1. 모든 결과에 확인됨 / 확인되지 않음 / 조회 범위 내 없음 / 충돌 중 하나를 붙이고, "확인됨"에는 무엇을 확인했는지 적는다.
2. 사람이 판단할 것(방향 선택, 법적 적용)과 AI 결과를 화면에서 구분한다.
3. 빠진 자료가 있어도 할 수 있는 작업은 끝까지 하고, 보류한 작업과 필요한 자료를 한곳에 모아 보인다.

|---|---|---|---|
| F1 | 필드별 추출 정확도 | 사람이 OA 원문으로 검수한 필드 | OA 20건 이상 (표본 OA + 학습데이터 표본) |
| F2 | 근거 검토 정량: 출처 존재·위치·판본 일치율, 주장 뒷받침 판정 정확도, 일부러 넣은 오류(없는 출처, 주장–원문 불일치, 다른 시점 판본을 적용으로 단정, 요지만 보고 전문이라 쓰기, 개정 전 기한을 현행처럼 쓴 글 — 예: 의견서 제출기간 개정. 정답의 날짜·기간은 공식 법령으로만 확정) 탐지율과 고친 비율 | 원문 대조 + 오류 주입 사례 | 실제 질문 + 오류 주입 사례 합쳐 20개 이상 |
| F3 | 심사관 지정 문단 회수율 (지정 번호를 입력에 주지 않고), 요소–문단 대조 정확도 | OA 지정 문단(불완전한 대리 정답) + 사람 검수 | 한국·미국 인용 지적 20개 이상 |
| F4 | 초안 오류 탐지 (번호·문단·조문 불일치 주입), 대응 누락 여부 | 오류 주입 | 초안 + 주입 오류 20개 이상 |
| 비교 | F2 근거 검토 역할 분리 있음/없음, F3 대조 방식: 품질 + 시간·비용·호출 수 | 같은 세트 | 위와 같음 |

- 기능마다 테스트 케이스 20개 이상. 성공 기준은 M1에서 첫 기준선을 잰 뒤 숫자로 정한다. 그 전에도 지킬 선: 없는 출처를 근거로 낸 답 0건, 확인하지 않은 원문 위치 표시 0건.
- 재지 않는 것: 사건에 대한 법적 적용 적절성, 대응 방향 우열, 보정 적법성. 변리사 평가자가 없어 결과 보고에 한계로 적는다.
- 실제 의견서·보정서가 있는 사건(예: 10-2022-0145521)은 "AI 초안과 실제 대응 비교"를 정성으로만 본다.
- 문서 대조로 확인할 수 있는 사실은 정답으로 쓴다. 예: 보정에서 종속항이 인용하는 항 번호가 바뀐 것, 의견서가 언급한 항 번호와 실제 보정 청구항의 불일치. 그 보정이 법적으로 충분한지는 재지 않는다.
- 세트는 tune(개발 중)과 report(마지막 한 번)로 나눈다 (저장소 CLAUDE.md).

## 8. 기능별로 필요한 자료
무엇을 어디서 받을지는 열어 둔다. 실제로 찾을 수 있는지는 데이터 수집에서 도메인 지식으로 확인하고, 필요한 게 생기면 더 받는다. 확정된 자료는 `data/<출처>.md` 데이터 카드로 쓴다 (이 PRD에서 쓰는 것만).

| 기능 | 필요한 자료 (종류) | 확인할 것 |
|---|---|---|
| F1 | 의견제출통지서 원문, 의견제출통지서 학습데이터(빈도 집계용) | OA 판 수·필드, 거절이유 빈도 |
| F1·F3·F4 | OA 당시 청구항(보정서), 최초 제출 명세서·도면, 실제 의견서·보정서 | 같은 사건으로 묶이는지(출원번호+발송번호/접수번호). 최초 명세서가 없으면 그 사건의 보정 근거 위치는 보류 |
| F3 | 한국·미국 인용문헌 전문과 문단 번호 | 지정 문단 위치 대조 가능 여부 |
| F2 | 특허법·시행령·시행규칙 (사건 시점 판과 현행, 부칙), 특허·실용신안 심사기준 (사건 시점 판과 현행), 판례·심결례 전문 | 판본·시행일, 원문 위치, 텍스트 추출 |
| 전체 | 자료별 이용 조건 | 저장·외부 LLM 전송·공개 시연 가능 여부 (KIPRIS Plus 답 대기, [questions.md](team/questions.md)). 답 전에는 표본 범위에서만, 원문 커밋 금지 |

- 첫 지원 거절이유는 학습데이터 빈도 집계를 본 뒤 3.2절에서 확정한다.

## 11. 에이전트 설계: 도구와 흐름이 갈리는 곳
### 11.1 도구 (후보, 구현 방식은 기술 구조에서)
| 도구 | 하는 일 | 입력 → 출력 | 데이터 | 기능 |
|---|---|---|---|---|
| OA 읽기 | OA에서 필드와 원문 위치를 뽑음 | OA PDF → 필드 + 쪽 위치 | 의견제출통지서 | F1 |
| 사건 자료 묶기 | 올린 자료를 같은 사건·판으로 묶고 빠진 것 표시 | 파일들 → 사건 자료 목록·판·미확인 | 보정서, 명세서 | F1 |
| 문헌 문단 검색 | 청구항 요소에 맞는 인용문헌 문단 찾기 | 요소 + 문헌 → 문단 후보 + 위치 | 한국·미국 인용문헌 | F3 |
| 법령 판본 조회 | 조문의 특정 시점 판 찾기 | 조문 + 기준일 → 그 판 본문·시행일 | 법령, 부칙 | F2 |
| 심사기준·판례 검색 | 질문에 맞는 문단 찾기 | 질문 → 문단 + 위치 + 판본 | 심사기준, 판례·심결례 | F2 |
| 근거 검증 | 출처가 있나, 위치·판본이 맞나, 주장을 뒷받침하나 | 주장 + 출처 → 판정 + 이유 | 위 자료 전부 | F2, F3, F4 |
| 청구항 비교 | 당시 청구항과 보정안의 바뀐 곳 | v0 + v1 → 바뀐 부분 (코드) | 청구항 | F4 |
| 초안 검사 | 번호·문단·조문 불일치, 대응 누락 | 초안 + F1~F3 결과 → 문제 목록 (코드) | - | F4 |

### 11.2 흐름이 갈리는 시나리오
| # | 상황 | 에이전트가 하는 일 |
|---|---|---|
| A | 최초 통지, 문헌 대조형 지적, 근거가 바로 안 나옴 | 요소별 대조 → 차이점 후보 → 근거가 없으면 다른 문단·도면 재조회 → 그래도 없으면 "조회 범위 내 없음"으로 두고 반박 위주 방향 후보 |
| B | 최후 통지, 문장 검토형 지적 | 보정 범위 제한을 먼저 걸고 → 심사기준 판본을 OA 통지일로 조회 → 판본을 모르면 사용자에게 확인 요청 → 제한 안에서만 보정 초안 |
| C | 인용문헌 하나가 없거나 지원 밖 나라 문헌 | 그 문헌 대조만 보류, 나머지 거절이유는 끝까지 진행, 필요한 자료를 모아 요청 |
| D | 사건 없는 법률 질문 | 시점이 없으면 현행으로 답하고 기준일 표시, 과거 시점이면 그 판을 찾고, 판본이 충돌하면 둘 다 보이고 확인 필요 표시 |

### 11.3 멈추는 조건과 사람 승인
- 재조회는 최대 횟수를 둔다 (숫자는 기술 구조에서). 도달하면 "미확인"과 찾아본 범위를 남기고 끝낸다.
- 사람이 해야 하는 것: 대응 방향 선택, 보정 초안 채택, 법률 근거를 사건으로 가져오기. 에이전트는 법적 결론·우열 추천·제출을 하지 않는다.
- 하네스(팀 규칙·Hook·서브에이전트·스킬)는 저장소 `CLAUDE.md`와 `.claude/`에 있다.
