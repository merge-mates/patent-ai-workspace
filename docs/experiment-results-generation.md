## 1. 설정
- 파이프라인: 확정 검색 후보(항 단위 + 확장 v2 + M4a + LLM 재순위, 근거 5개, 조문당 4,000자) → Claude가 `{status, answer, cited}` JSON으로 답 → 코드 검증. 두 모델 모두 **같은 검색 결과**(`data/processed/gen_retrieval_dev.json`)와 같은 프롬프트(해시는 결과 파일 config)를 썼다. 모델만 한 변수.
- 질문: 정답 있음 개발 47개(`questions_d2_dev.jsonl`), 정답 없음 개발 11개(`questions_d2_noanswer.jsonl`의 split=dev2). 봉인 세트는 쓰지 않았다.
- 결과 파일: `data/results/gen_claude-haiku-5-5_questions_d2_dev_20261113-101241.{json,md}`, `gen_claude-sonnet-5-5_questions_d2_dev_20261113-101307.{json,md}`. (같은 날 먼저 돌린 `…-091725`(스모크)와 `…-100535`는 검증 규칙과 타임아웃 처리를 고치기 전 결과라 비교에서 제외.)

## 3. 사람이 읽은 표본(근거 충실성)
읽은 것: 정답 없음에 답을 만든 6개 질문의 두 모델 답변, 상태가 갈린 질문 8개 중 4개(N24, V17, V22, S32), 부분 답변 질문 N13·N33, 검증 경고 1건.
- **정답 없음에 `partial`로 답한 사례는 대부분 정직한 부분 답변이었다.** 예: N26(직무발명 승계·보상)은 두 모델 모두 특허법 제38조의 일반 승계 절차를 설명하고 "직무발명 특유 요건·보상 기준은 제공된 조문에 없다(발명진흥법 소관으로 보이나 확인 불가)"고 분명히 말했다. S24, N38, S36도 핵심 정보(납부서 기재 항목, 등록 신청 서류, 보정 표시 방식)가 조문에 없다고 명시했다. 다만 설계 7번 규칙("정답 없음에 answered/partial이면 답을 만들어 냄")으로 세면 위 수치가 나온다. 사용자가 정한 정책("정답 없으면 근거 없다고 알려 준다")과 맞게 `no_basis`로만 답하게 할지, 관련 조문을 설명하는 부분 답변을 허용할지는 아직 정하지 않았다.
- **haiku는 `partial`을 훨씬 자주 쓴다(28 대 20).** 상태가 갈린 8개는 모두 haiku `partial` / sonnet `answered`. 읽은 4개 중 N24·V17은 haiku의 "확실하지 않은 부분"이 질문과 직접 관련 없는 것(예: 신청 사유 제한)이거나 지나치게 조심스러웠고, sonnet의 답은 근거에 충실했다. S32(등록원부 열람 절차)는 sonnet이 `answered`로 썼지만 열람 신청 절차까지 다 답했는지는 확인하지 못했다(과장일 수 있음).
- **검증 경고 1건(haiku N10)은 오경보로 보인다.** 답변의 "제40조 계열"은 근거 조문 "시행규칙 제106조의40"을 가리킨 표현이다.
- **화면용으로 고쳐야 할 점:** 두 모델 모두 답변 글 안에 `(E1)`, `(E2 ③)` 같은 꼬리표를 남긴다. 사용자에게는 보이지 않게 지우거나 조문 이름으로 바꾸는 표시 계층이 필요하다(프롬프트로 막을 수도 있으나 이번 평가 설정에서는 바꾸지 않았다).

## 4. 한계
- 정답 없음 11개·부분 답변 3개로 표본이 작다. 1~2개 차이는 해석하지 않는다.
- 근거 충실성은 코드 검증과 내가 읽은 일부 표본으로 봤다. 전수 검토나 사람 전문가 검토는 아니다.
- 정답·질문이 LLM이 만든 것이고, 생성 모델(Claude)과 검색 모델(GPT)은 분리했지만 정답 지정은 Claude 에이전트라 같은 계열의 관대함이 완전히 분리된 것은 아니다.
- 비용은 측정하지 않았다(sonnet이 haiku보다 비싼 것은 일반적인 가격 차이로 보이나 이번에 확인하지 않음).
- 개발 평가 중 한 번 고친 것: 첫 실행에서 검증 경고 11개가 전부 오경보였고(답변이 근거 본문이 인용한 조문을 되풀이) 규칙을 정밀화했으며, 한 요청이 응답 지연으로 실패해 타임아웃 재시도를 추가했다. 두 수정 뒤 두 모델을 같은 조건으로 다시 돌린 결과가 위 표다.

- 프롬프트 v2("질문이 묻는 핵심 사항을 조문이 다루지 않으면 no_basis")를 sonnet으로 개발 질문에 한 번 돌린 결과(`gen_claude-sonnet-5-5-v2_questions_d2_dev_20261113-102700`): 정답 있음은 v1과 같다(정답 조문 인용 45/47, answered 27, partial 20, no_basis 0, 검증 경고 0). 정답 없음 11개는 no_basis 5 → 8, 답을 만든 것 6 → 3(N47, S34, S36). 의도대로이며 정답 있는 질문에는 영향이 없었다.

### 6-3. 읽은 사례
- 부분 답변 질문 N44(보정서 기재 항목·제출 방법), N45(특허료 감면 서류·대상)는 v1·v2 모두 `partial`로 "근거로 확인되는 부분 / 제공된 조문으로는 확실하지 않은 부분"을 나눠 썼다. 지어낸 수치는 없었다.
- 정답 없음에서 v2도 `partial`로 남은 S22(도면 작성 기준), S35(감면 증명서류), S40(반환 청구서 기재사항)는 모두 핵심 사항이 조문에 없다고 분명히 밝히면서 관련 조문이 다루는 범위를 설명했다. 설계 7번 규칙으로는 "답을 만듦"에 들지만 내용은 정직한 부분 답변이었다.
- **라벨 경계의 불확실성:** S35(감면 증명서류, 정답 없음)와 N45(감면 서류·대상, 정답 있음 제83조, 부분 답변)는 거의 같은 내용을 묻는데 정답 지정 결과가 다르다. "부분 답변"과 "정답 없음"의 경계가 흐려서, 정답 없음 지표는 원래 잡음이 크다. 정답 없음 7개라 1개 차이도 14%p다.
- v2가 N30을 `partial`로 바꾼 것이 바람직한지는 확인하지 못했다.

### 6-4. 한계
- 표본이 작다(정답 있음 25, 정답 없음 7). 정답 없음은 위 라벨 경계 문제로 잡음이 크다.
- 두 프롬프트를 봉인에서 둘 다 보고 선택했으므로 채택된 v2의 봉인 수치는 약간 낙관적이다(선택 규칙은 평가 전에 선언).
- 정답·질문이 LLM이 만든 것이고, 근거 충실성은 코드 검증과 일부 표본 읽기로만 봤다. 사람 전문가 검증은 없다.
- 질문당 호출이 4번이라 총 소요는 검색 5초 + 생성 6~7초(평균)이고, 비용은 측정하지 않았다.

## 7. 프롬프트 v3: 존댓말 규칙 (2026-11-13)
- **문제:** 화면에서 첫 질문은 존댓말, 두 번째 질문은 반말("~할 수 있다")로 답이 나왔다(사용자 발견). v1·v2 프롬프트는 "한국어로"만 말하고 말투를 정하지 않았다. 기존 평가 답변을 문장 끝으로 추정해 보면 반말체가 더 많은 답변이 sonnet v2 개발 58개 중 15개, 봉인 32개 중 12개, sonnet v1 개발 35개였다(추정 지표).
- **수정:** 프롬프트 v3 = v2 + 6번 규칙만 "한국어 존댓말(~합니다, ~해요)로 … 조문 문장을 옮기거나 요약할 때도 문장 끝을 존댓말로 쓰고 ~한다, ~있다로 끝내지 않는다". v2는 평가에 쓴 것이라 해시로 고정하고 v3는 v2와 6번 규칙 외에 글자까지 같음을 테스트로 확인. 평가 요약에 "반말체 추정" 지표 추가.
- **개발 질문 확인**(sonnet-5-5, 같은 검색 결과, `gen_claude-sonnet-5-5-v3_questions_d2_dev_20261113-114632`): 반말체 추정 정답 있음 14 → 0, 정답 없음 1 → 0. 정답 조문 인용 45/47 그대로, answered 27·partial 20·no_basis 0 그대로. 정답 없음 11개는 no_basis 8 → 7, 답을 만든 것 3 → 4(S39 한 개가 no_basis → partial로 바뀜, 한 개 차이는 잡음으로 봄). 검증 경고 0 → 1(N01의 목록 번호 "5."를 근거에 없는 숫자로 오인한 오경보, 알려진 숫자 검증의 한계).
- **결정:** 기본 프롬프트를 v3로 바꿨다. 말투 규칙 하나만 바꾼 것이고 개발 지표가 달라지지 않아 봉인 세트는 다시 쓰지 않았다(봉인 수치는 v2 기준). 한계: 말투 지표는 문장 끝 규칙의 추정이며 완벽한 판정이 아니다.
