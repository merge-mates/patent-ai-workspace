# 인용문헌 문단 찾기: 문헌 통째 LLM vs 하이브리드 RRF (이슈 #248)

**가설**: 그 OA 인용문헌 안에서 문단을 찾는 일은 문헌을 통째로 LLM에 넣어도 하이브리드 검색만큼 맞힌다. 그러면 F3 대비에서 검색이 꼭 필요한지 답이 나온다.
**종류**: 구현 비교 (같은 검색 계약 뒤 `impl`만 다름)
**설정**: `config/cite_rank.yaml` `whole_doc` (claude-haiku-5-5, effort medium, max_tokens 16000, 출력 검사 실패 때 1회 더), 프롬프트 `prompts/cite_rank/whole_doc.md`. 범위 (a) "그 OA 인용문헌 안"만 (노이즈 범위는 줄마다 20만 토큰을 넘어 재지 않음). 색인 cite-idx-v2 (16문헌 1,998조각, 지문 aa2a82ee… 기준선과 같음).
- 같은 설정 2회, 회마다 새 캐시 폴더 (git 밖 `work/cite_whole_doc/cache_run{1,2}`). 11/22 새벽 git 밖 시제품 캐시는 쓰지 않음.
- scores.json은 1회차. 2회차는 git 밖 `work/cite_whole_doc/run2/scores.json`. 줄별 결과·CQ 후보도 `work/cite_whole_doc/run{1,2}/`.
- 코드: feat/248-cite-search-whole-doc 0723d69. 실행 전 `count_tokens`(무료)로 69요청 입력 1,957,766 토큰, 최대 64,649 (10만 넘는 요청 0 → Haiku $0.10/$0.50 단가 구간, claude-api 스킬 모델 표 2026-11-03).

## 흔들림 (같은 설정 2회)
- 점수 차이: Hit@1·3·10 0.015 (1줄), Hit@5 0.029 (2줄), Recall@10 0.041.
- 줄 단위로는 더 흔들린다: 첫 정답 순위가 같은 줄 40/68, Hit@1이 뒤집힌 줄 7, Hit@10이 뒤집힌 줄 9 (뒤집힌 줄이 서로 상쇄돼 합계 차이가 작다). CQ 겹침 12 (1회 17, 2회 16).

## 해석 (Claude 초안, 재아 확인 필요)
- **위쪽 순위(Hit@1·3)는 통째 LLM이 분명히 낫다**: Hit@1 +0.21 (14줄 안팎)이 시제품 포함 3회 모두 같은 쪽이고, 2회 차이(0.015)보다 훨씬 크다.
- **Hit@10은 흔들림 안**: 2회 평균 +0.051 (3~4줄)이지만 시제품 포함 3회 범위 0.691~0.765가 RRF 0.706을 품는다. "하이브리드만큼 맞힌다"(가설)는 맞고, "더 낫다"는 이 세트 크기(68줄)로 말할 수 없다.
- **두 방식이 다른 줄을 맞힌다**: 둘 다 못 찾은 줄은 5~8개뿐이고, 합집합 Hit@10이 0.88~0.93이다. 섞는 방식(하이브리드 상위 후보 → LLM 재순위)이 다음 후보다 (판단).
- **비용·시간**: 회당 $0.21·232초로 RRF(호출 0·13초)보다 크다. 줄마다 문헌 전체(평균 2.9만 토큰)를 넣기 때문이고, 범위가 넓은 노이즈 B(문헌 평균 10.6개)에는 그대로 못 쓴다 (줄마다 20만 토큰 넘음).
- 출력 검사 실패·버린 번호는 2회 모두 0이라 not_extracted 처리(못 맞힌 줄로 셈)는 이번 점수에 영향이 없다.
