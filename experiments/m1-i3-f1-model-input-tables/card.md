# read_oa 모델 입력에 쪽 넘은 표를 마크다운으로 덧붙이기 (이슈 #122 task-b)

**가설**: 쪽을 넘은 거절이유 표 칸이 모델 입력에서 끊겨 보인다. 이어 붙인 표(merged_tables)를 쪽 끝에 마크다운으로 덧붙이면, 그 표에 기대는 값(대상 청구항, 청구항 줄)이 덜 빠진다.
**종류**: 설정 비교
**바꾼 것 (하나)**: `settings.model_input`: `raw` → `tables_md`. 프롬프트에 표 안내 한 줄도 같이 들어갔다(raw 실행 뒤에 더한 줄).

## 결과 (scores.json)
값(ExtractedValue)과 청구항 줄(ClaimRow)의 status 개수다. 결과·거절이유 모음 status, evidence, 검토할 사항은 뺐다. 정답과 맞춰 본 것이 아니라 "확인됨"이 곧 "맞음"은 아니다.

|---|---|---|---|
| 확인됨 | 99 | 94 | -5 |
| 확인되지 않음: 못 뽑음 | 27 | 26 | -1 |
| 확인되지 않음: 애매 | 5 | 11 | +6 |
| 경고 "청구항 번호를 못 읽은 줄" (5건) | 5 | 0 | -5 |
| 그중 칸이 쪽 중간에서 잘린 사건 (거절이유 3) | 4 | 0 | -4 |
| 비용($) | 약 0.034 (6회) | 0.032 (6회) | |
| 외부 API 호출 | 6 | 6 (출력 검사 실패 재시도 1) | |

|---|---|---|---|
| case1 | 20 / 2 · 1 | 22 / 1 · 0 | 쪽 넘는 표 없음 |

| case4 | 12 / 0 · 0 | 11 / 1 · 0 | 쪽 넘는 표 없음 |

## 실패 유형 (개수)
| 유형 | raw | tables_md |
|---|---|---|
| 청구항 번호를 못 읽은 줄 (줄을 안 만듦) | 5 | 0 |
| 출력 검사 실패 재시도 | 1 | 1 |

## 해석
- 표와 관계있는 곳은 좋아졌다.
  - case5 거절이유 3: 모델이 줄마다 청구항 번호를 냈다(raw는 번호 칸이 비어 경고 4번). 경고가 0이 됐다.
  - case3 거절이유 3: 청구항 줄과 인용 위치가 확인됨으로 바뀌었다.
- 그런데 case5의 확인됨은 26에서 20으로 줄었다. 바뀐 칸은 청구항 줄 5개(거절이유 2·3)와 거절이유 2 요지다.
  - 판단 문장 원문 대조는 모두 통과한다(기록된 모델 응답으로 다시 확인, 모델 호출 없음). 원인은 표 입력이 아니라 청구항 줄 합치기 쪽으로 보인다. 경고는 "같은 취지 대상 줄 claim:1이 확인되지 않음" 3번이다(판단). 아직 끝까지 보지 않았다.
- 주의
  - temperature는 API에서 빠져 고정할 수 없다(#134). 이 실행도 temperature 없이 보냈고, 같은 입력에도 답이 흔들린다. 설정에 적어 고정할 수 있는 것은 effort(이번은 기본 medium)뿐이다.
  - 그래서 표와 관계없는 칸의 변화는 판단에서 뺐다: case1·case2·case4 전부, case5의 거절이유 2.
  - 한 번씩만 돌려서 흔들림의 크기는 모른다.
- 결론(판단): 표 덧붙이기는 쪽을 넘은 표 2건에서 의도한 효과(청구항 번호·청구항 줄)를 냈다. 전체 확인됨 개수는 흔들림과 섞여 좋아졌다고 말할 수 없다. 기본값을 tables_md로 바꿀지는 정답 대비 채점(#20) 전에는 사람 판단이다.
- 결정 (11/19): 기본값은 raw로 둔다. Claude 의견이 갈렸다: 맥 세션은 tables_md(쪽 넘은 표의 번호 칸 경고가 사라짐), 프로젝트 스레드는 raw(확인됨 99 → 94와 temperature 흔들림 때문에 증거 부족). 재아가 raw를 골랐다. tables_md는 #20 채점기 뒤 정답 대비로 다시 본다.

## 해 본 것 / 버린 것
- 머리말·꼬리말 정제: 모델 입력에서 정답 글자가 보이는 수가 그대로(56/58)라 이번엔 뺐다(보류).
- 본문에서 표 글자 빼기(A안): 공유 스키마 변경이 필요해 미뤘다. 섞인 표 글자 때문에 모델이 틀리는 사례가 나오면 다시 본다.
