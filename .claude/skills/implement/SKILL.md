# 구현: $ARGUMENTS

## 계획 고르기
- 첫 인자가 `tasks.md` 경로면 **계획 모드**: 그 파일의 이슈 계획 `$1`이 계획이고, 진행은 그 계획의 진행 칸에 쓴다.
- 첫 인자가 숫자면 **작은 이슈 모드**: 이슈 #$0 본문이 계획이다 (`gh issue view $0 --json title,body`). task = 본문의 task 체크리스트 한 줄, 합격 기준 = 본문 `합격 기준`, 확인 방법 = 본문 `확인 명령`. 진행은 이슈 본문 체크박스에 쓴다 (아래 8번). 두 번째 인자가 있으면 그 task부터.
  - 본문 `구현 계획` 칸에 tasks.md 링크가 있으면 작은 이슈가 아니다. 멈추고 그 tasks.md로 부르라고 알린다.
  - task 체크리스트나 `확인 명령`이 없으면 멈추고 사람에게 넣어 달라고 한다 (CLAUDE.md 일하는 순서 1번: 그 둘이 구현 계획이다).

## 시작 전
1. 지금 브랜치가 `main`이면 `/start <이슈번호>`로 브랜치를 만든다 (이슈 번호는 계획 제목 옆에 있다. 브랜치 `<type>/<이슈번호>-<짧은설명>`, 보드 카드 In Progress). 브랜치 하나 = 계획 하나 = PR 하나 (이슈 하나에 계획 여러 개 가능).
2. `git status`가 깨끗한지 본다. 커밋 안 한 변경이 있으면 멈추고 사람에게 묻는다 (implementer 커밋에 섞이지 않게).
3. 계획 모드: 그 이슈 계획 머리의 `상태:` 줄이 `승인`인지 본다 (`/plan-feature`가 계획마다 적는 줄). 아니면 멈춘다. 작은 이슈 모드: 이슈가 열려 있고 담당자가 나인지 본다 (승인 줄은 없다. 이슈 본문을 사람이 쓴 것이 승인이다).
4. 계획의 task 목록과 진행 칸(작은 이슈면 본문 체크박스)을 읽는다. 시작 task 인자가 있으면 그 task부터.

## task 반복 (겹치지 않는 task는 동시에, 한 묶음씩)
1. **묶음 고르기**: 먼저 끝나야 할 task가 다 끝났고 고칠 파일이 서로 겹치지 않는 task들을 한 묶음으로 잡아 동시에 한다. 겹치는지 애매하면 순서대로 한다 (묶음 하나에 task 하나).
2. **구현**: implementer 에이전트에 넘긴다. 넘길 것은 그 task 항목만, 그 기능 requirements의 해당 합격 기준(작은 이슈면 이슈 본문 합격 기준과 확인 명령), 고칠 폴더.
   - task 하나: `git rev-parse HEAD` → `<시작>`을 적어 두고 implementer를 이 폴더에서 부른다. 이 task의 변경은 `git diff <시작>..HEAD`.
   - 동시 묶음: Agent 도구의 `isolation: "worktree"`로 task마다 implementer를 각자 워크트리에서 한꺼번에 부른다. 같은 폴더에서 동시에 고치면 덮어쓴다.
3. **가져오기** (동시 묶음만): 모두 끝나면 계획 순서대로 task마다 `git rev-parse HEAD` → `<시작>`을 적고, 그 워크트리의 커밋을 이 브랜치로 `git cherry-pick` 한다. 충돌이 나면 겹친 것이니 멈추고 사람에게 넘긴다. 다 가져온 뒤 그 폴더 전체 테스트를 돌린다.
4. implementer 보고를 받는다. "막힘"이거나 "목적이 다른 일이라 나누자"면 진행 칸 `막힌 것`에 적고(작은 이슈 모드면 진행 칸이 없으니 이슈 댓글 `gh issue comment $0`로 남긴다) 사람에게 넘긴 뒤 멈춘다.
5. **보고를 믿지 않고 직접 확인한다**: 보고가 비었거나 칸이 빠졌으면 `git log`, `git show --stat`, 테스트를 직접 돌려 본다.
6. task마다 **code-reviewer 에이전트**(task 모드)에 넘긴다: task 항목, 합격 기준, `git diff <시작>..HEAD`. implementer 보고는 넘기지 않는다.
7. 막음이 있으면 implementer에게 지적만 넘겨 고치게 하고 (이 폴더에서), 테스트를 다시 돌리고, code-reviewer가 **바뀐 부분만** 다시 본다. 최대 2회. 그래도 막음이 남으면 멈추고 사람에게.
8. 그 폴더 전체 테스트가 통과하는지 다시 본다 (코드 커밋은 implementer가 이미 했다). 진행을 적는다:
   - 계획 모드: 진행 칸에서 task를 `[x]`로, `다음`을 고쳐 따로 커밋한다: `docs(docs): <기능> $1 task N 진행`.
   - 작은 이슈 모드: 커밋은 없다. 이슈 본문의 그 task 줄을 `- [x]`로 바꾼다 (`gh issue view $0 --json body -q .body` → 그 줄만 바꿔 `gh issue edit $0 --body-file <파일>`. 다른 줄은 그대로 둔다). 실패하면 사람에게 알리고 다음 task로 가지 않는다.
9. 안 끝난 task가 남았으면 1로 돌아간다.

## 이슈가 끝나면
1. `/check 이슈 $0 $1`(작은 이슈면 `/check 이슈 $0`)로 **문서 대조 점검**과 이슈 전체 리뷰를 한다.
2. AI 동작을 바꾼 이슈면 `/experiment`로 tune 세트 점수 한 줄을 낸다 (돌리기 전에 비용을 말하고 사람에게 묻는다). task마다는 내지 않는다.
3. 끝에 내놓을 것 (PR 본문 재료):
```
- 합격 기준: (기준 → 테스트 이름 → 통과)
- 돌려 볼 명령:
- 점수·비용: (AI면)
- 설계와 다르게 한 곳과 이유:
- 남은 것: (참고 지적, 다음 이터레이션으로)
```
4. `/pr-draft`로 PR 제목·본문을 만들어 사람에게 보여 준다. 사람이 OK하면 Claude가 push와 PR 생성을 한다.
